# Техническое задание  
## Интернет-магазин строительных и промышленных материалов

**Версия:** 2.0  
**Статус:** основное техническое задание  
**Тип первой поставки:** Frontend MVP с тестовым API  
**Целевая архитектура:** React storefront + Go REST API

---

## 1. Назначение проекта

Разработать расширяемый интернет-магазин строительных и промышленных материалов для реального коммерческого использования.

Проект создаётся поэтапно. Первая версия представляет собой MVP каталога и локальной корзины. Архитектура должна позволять в дальнейшем добавить реальные заказы, оплату, доставку, личный кабинет, административную панель, импорт из 1С и мобильное приложение без полного переписывания системы.

Основные приоритеты:

1. предсказуемые границы MVP;
2. качество и читаемость кода;
3. стабильный API-контракт;
4. удобство пользователя;
5. адаптивность;
6. доступность;
7. SEO публичного каталога;
8. производительность;
9. безопасность;
10. возможность дальнейшего расширения.

Термин `production-ready` не используется как самостоятельный критерий приёмки. Все требования должны проверяться через конкретные сценарии, тесты и измеримые показатели.

## 2. Этапы развития проекта

### 2.1. Этап A. Frontend MVP

Включает:

- главную страницу;
- дерево категорий;
- общий каталог;
- страницу категории;
- страницу товара;
- варианты товара;
- локальную корзину;
- сохранение корзины;

- адаптивную вёрстку;
- основные SEO-метаданные;

Не включает:

- регистрацию;
- вход;
- личный кабинет;
- реальное оформление заказа;
- создание заказа на сервере;
- оплату;
- доставку;
- промокоды;
- избранное;
- отзывы;
- админ-панель;
- импорт из 1С;
- реальные складские остатки.

### 2.2. Этап B. Коммерческий релиз

Планируется добавить:

- создание заказа без обязательной регистрации;

- выбор способа получения;
- подтверждение заказа;

- юридические страницы;
- аналитику и мониторинг;

### 2.3. Этап C. Полная e-commerce-платформа

Планируется добавить:

- авторизацию;
- личный кабинет;
- историю заказов;
- онлайн-оплату;
- интеграции доставки;
- избранное;
- отзывы;
- систему скидок;
- бонусную программу;
- несколько складов;

- импорт из 1С;

- мобильное приложение.

## 4. Технологический стек

### 4.1. Frontend

Обязательный стек:

- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query;
- Zustand;
- MSW;
- Zod;
- ESLint;
- Prettier;
- Vitest;
- React Testing Library;
- Playwright.

Подход к стилям:

- Tailwind CSS либо CSS Modules;
- в рамках проекта используется только один основной подход;
- решение фиксируется до реализации дизайн-системы.

### 4.2. Backend

Целевой backend:

- Go;
- REST API;
- PostgreSQL;
- DTO между API и внутренними моделями;
- отдельные уровни transport, application, domain и infrastructure.

Конкретная внутренняя структура Go-проекта не является частью Frontend MVP, но бизнес-логика не должна находиться непосредственно в HTTP handlers.

### 4.3. HTTP-клиент

Разрешается использовать:

- нативный `fetch` с общей обёрткой;
- либо Axios.

В проекте используется только один HTTP-клиент.

HTTP-запросы не выполняются непосредственно внутри UI-компонентов.

### 4.4. Формы

React Hook Form используется после появления настоящих форм:

- оформление заказа;
- авторизация;
- обратная связь;
- административные формы.

Для MVP каталога библиотека не должна подключаться только ради будущего использования.

## 5. Архитектура рендеринга и SEO

### 5.1. Режим разработки MVP

На локальном этапе допустим SPA-режим с MSW.

### 5.2. Публичный production

До публичного запуска необходимо обеспечить SSR или статический prerendering для:

- главной страницы;
- страниц категорий;
- карточек товаров;
- информационных страниц.

Корзина может оставаться клиентской.

Рекомендуемая реализация:

- React Router Framework Mode;
- Vite как сборщик;
- SSR для динамических страниц;
- prerendering для статических страниц.

### 5.3. HTTP-статусы

Публичные страницы должны возвращать корректные HTTP-статусы:

- `200` для существующей страницы;
- `404` для отсутствующего товара или категории;
- `500` при необработанной серверной ошибке.

Нельзя возвращать обычный `200` со страницей «товар не найден» для несуществующего товара.

## 7. Страницы

### 7.1. Главная страница

Содержит:

- основной баннер;
- краткое описание магазина;
- основные категории;
- популярные или рекомендуемые товары;
- преимущества;
- способы связи;
- Header;
- Footer.

Если популярные товары не определены API, блок скрывается. Нельзя случайным образом выбирать товары на frontend.

### 7.2. Общий каталог

Содержит:

- хлебные крошки;
- заголовок первого уровня;
- дерево или список категорий;
- сетку товаров;
- пагинацию;
- необязательную сортировку;
- загрузочное состояние;
- пустое состояние;
- состояние ошибки;
- кнопку повторной попытки.

### 7.3. Страница категории

Содержит:

- хлебные крошки;
- название категории;
- описание категории при наличии;
- дочерние категории;
- товары;
- пагинацию;
- сортировку;
- подготовленное место для будущих фильтров.

### 7.4. Страница товара

Содержит:

- хлебные крошки;
- галерею изображений;
- заглушку изображения;
- название товара;
- артикул выбранного варианта;
- цену;
- старую цену при наличии;
- единицу измерения;
- наличие;
- селекторы вариантов;
- управление количеством;
- кнопку «В корзину»;
- технические характеристики;
- описание;
- информацию о минимальном количестве и шаге заказа;
- ссылку назад в категорию.

Если вариант не выбран, кнопка добавления должна быть отключена либо интерфейс должен автоматически выбрать допустимый вариант по умолчанию.

Недоступные комбинации характеристик должны быть отключены.

### 7.5. Корзина

Содержит:

- список позиций;
- изображение;
- название товара;
- название варианта;
- артикул;
- цену;
- единицу измерения;
- количество;
- управление количеством;
- стоимость позиции;
- общую сумму;
- удаление позиции;
- очистку корзины;
- кнопку оформления;
- предупреждение об изменении цены или доступности.

Для MVP кнопка оформления показывает сообщение:

> Оформление заказа скоро появится. Пока вы можете уточнить наличие и актуальную цену у менеджера.

Допускается добавить кнопку связи с менеджером, если утверждены телефон, электронная почта или мессенджер.

│
├── features/

- импорты между слоями соответствуют правилам FSD;
- не создавать отдельную feature для каждого обработчика кнопки, если отдельной бизнес-функции фактически нет.

## 11. Стандарты TypeScript и кода

Обязательно:

- TypeScript strict mode;
- запрет неаргументированного `any`;
- типизация API-ответов;
- runtime-валидация внешних данных через Zod в критических местах;
- ESLint;
- Prettier;
- абсолютные алиасы импортов;
- отсутствие неиспользуемого кода;
- отсутствие прямого доступа к `import.meta.env` вне слоя конфигурации.

Допускается `unknown` с последующим безопасным сужением типа.

Ограничение 200–300 строк не является абсолютным. Файл разделяется по ответственности, а не только по числу строк.

Принципы SOLID, DRY, KISS и YAGNI применяются совместно. Нельзя устранять небольшое повторение ценой сложной универсальной абстракции.

## 13. API-контракт

API версионируется:

```text
/api/v1
```

Контракт хранится в OpenAPI.

OpenAPI-файл является источником истины для:

- путей;
- параметров;
- DTO;
- кодов ответа;
- схем ошибок.

Frontend mock-данные и Go API должны соответствовать одной схеме.

### 13.1. Категории

```text
GET /api/v1/catalog/categories
GET /api/v1/catalog/categories/{slug}
```

### 13.2. Товары

```text
GET /api/v1/catalog/products
GET /api/v1/catalog/products/{slug}
```

Параметры списка:

```text
category
search
sort
page
limit
filter[attributeCode]
```

Допустимые значения `sort`:

```text
relevance
price_asc
price_desc
name_asc
name_desc
```

Нельзя передавать непрозрачный параметр `filters` без согласованного формата.

### 13.3. Восстановление корзины

```text
POST /api/v1/catalog/variants/resolve
```

Запрос:

```json
{
  "variantIds": ["variant-1", "variant-2"]
}
```

Ответ:

```text
{
  items: CartResolvedVariant[],
  missingVariantIds: string[]
}
```

### 13.4. Пагинация

```text
{
  items: ProductListItem[],
  pagination: {
    page: number,
    limit: number,
    total: number,
    totalPages: number
  }
}
```

### 13.5. Ошибки

Единый формат:

```text
{
  error: {
    code: string,
    message: string,
    details: unknown | null,
    requestId: string | null
  }
}
```

Frontend показывает пользователю безопасное сообщение и не выводит stack trace или внутренние данные сервера.

### 13.6. Коды ответов

| Код | Использование |
|---|---|
| `200` | Успешное получение |
| `400` | Некорректный запрос |
| `404` | Ресурс не найден |
| `409` | Конфликт состояния |
| `422` | Ошибка валидации |
| `429` | Слишком много запросов |
| `500` | Внутренняя ошибка |
| `503` | Временная недоступность |

## 15. Работа с серверными данными

TanStack Query используется для:

- кэширования;
- загрузочных состояний;
- повторных запросов;
- инвалидации;
- фонового обновления;
- дедупликации запросов.

Требования:

- query keys централизованы;
- retry не выполняется бесконечно;
- `404` не повторяется автоматически;
- сетевые ошибки и `500` обрабатываются отдельно;
- `staleTime` определяется по типу данных;
- категории кэшируются дольше товаров;
- запросы не дублируются между страницей и компонентами;
- данные API не копируются в Zustand без необходимости.

Zustand используется только для клиентского состояния, прежде всего корзины.

## 16. Корзина

### 16.1. Хранение

- Zustand;
- persist middleware или эквивалент;
- localStorage;
- версия схемы хранилища;
- миграция при изменении структуры;
- безопасное восстановление после повреждения данных.

Ключ:

```text
storefront-cart-v1
```

### 16.2. Бизнес-правила

- позиция идентифицируется по `variantId`;
- повторное добавление увеличивает количество;
- количество изменяется с учётом `quantityStep`;
- количество не может быть меньше `minOrderQuantity`;
- при наличии максимального количества оно не превышается;
- недоступный вариант нельзя добавить;
- изменение количества проходит нормализацию;
- очистка корзины требует подтверждения;
- итог рассчитывается только для вариантов с известной фиксированной ценой;
- товары с ценой по запросу отображаются отдельно;
- итоговая цена считается предварительной;
- цена и наличие повторно проверяются при восстановлении корзины.

### 16.3. Некорректные позиции

Если вариант:

- удалён;
- архивирован;
- не найден;
- стал недоступен;
- изменил единицу продажи;

пользователь получает понятное уведомление.

Такая позиция не должна приводить к падению страницы.

## 18. Производительность

Оптимизация выполняется на основе измерений.

Целевые Core Web Vitals для production на 75-м перцентиле:

- LCP не более 2,5 секунды;
- INP не более 200 мс;
- CLS не более 0,1.

Требования:

- lazy loading маршрутов;
- code splitting по страницам;
- размеры изображений задаются заранее;
- изображения оптимизируются;
- поддерживаются WebP или AVIF с fallback при необходимости;
- основное изображение товара не загружается через обычный lazy loading, если является LCP-элементом;
- шрифты не вызывают значительный layout shift;
- skeleton соответствует размеру будущего контента;
- тяжёлые библиотеки не добавляются без необходимости;
- bundle анализируется перед production-релизом.

Memoization, virtualization, preload и prefetch используются только при наличии измеримой пользы.

Виртуализация не требуется для небольшого списка товаров.

## 20. Безопасность

### 20.1. Frontend MVP

Обязательно:

- не использовать `dangerouslySetInnerHTML` без отдельной проверки;
- не помещать секреты в frontend environment variables;
- не хранить чувствительные данные в localStorage;
- не показывать внутренние ошибки сервера;
- валидировать данные внешнего API;
- защищаться от open redirect;
- не строить URL из непроверенных пользовательских значений;
- обновлять зависимости;
- включить безопасные заголовки на сервере раздачи frontend;
- использовать HTTPS в production.

### 20.2. Будущая авторизация

При добавлении авторизации:

- не хранить долгоживущий JWT в localStorage без отдельного обоснования;

- защищать state-changing запросы;
- проверять авторизацию на сервере;
- frontend-проверка прав не считается защитой.

### 20.3. Backend

Go API отвечает за:

- аутентификацию;
- авторизацию;
- контроль доступа;
- валидацию DTO;
- защиту от SQL Injection;
- rate limiting;
- CORS;
- безопасные cookies;
- ограничение размера запросов;
- безопасную обработку файлов;
- защиту административного API;
- сокрытие внутренних ошибок;
- журналирование действий администраторов.

## 28. Критерии приёмки MVP

MVP считается принятым, если:

- все маршруты работают;
- данные не импортируются напрямую из fixtures в компоненты;
- MSW отключается конфигурацией;
- интерфейс не требует переписывания при подключении Go API;
- категории строятся динамически;
- список товаров использует облегчённый DTO;
- страница товара отображает полные данные;
- пользователь может выбрать допустимый вариант;
- пользователь может добавить вариант в корзину;
- повторное добавление объединяет позиции;
- количество учитывает шаг и минимальное значение;
- корзина восстанавливается после обновления;
- отсутствующие варианты обрабатываются безопасно;
- цена отображается в рублях;
- общая сумма рассчитывается корректно;
- товар без фиксированной цены не ломает итог;
- очистка требует подтверждения;
- оформление показывает заглушку;
- loading, empty, error и 404 реализованы;
- мобильная версия работает от 320 px;
- основные действия доступны с клавиатуры;
- lint, typecheck, tests и build проходят;
- нет неутверждённых функций авторизации, оплаты и реальных заказов;
- OpenAPI-контракт зафиксирован;
- тестовые данные соответствуют контракту;
- frontend не содержит секретов;
- production build не включает MSW.
