# ADR-0001: Гибридная стратегия рендеринга storefront

## Status

Accepted

Дата: 2026-07-30.

Решение фиксирует целевую production-архитектуру. Его реализация вынесена в отдельную
миграционную задачу и не входит в этап 9.

## Context

Текущий Frontend MVP — React + Vite SPA с клиентским React Router, TanStack Query и
локальным MSW. Этот режим подходит для разработки и демонстрации, но HTML до выполнения
JavaScript не содержит маршрутного контента, а статический сервер не может вернуть
корректные маршрутные статусы `404` и `500`.

`tz.md` требует до публичного запуска SSR или prerendering главной, категорий, товаров и
информационных страниц, а также корректные HTTP-статусы. Актуальный нормативный раздел
`Rendering Strategy` в `frontend_architercture.md` уже задаёт ту же поэтапную стратегию:
SPA только для MVP, затем SSR динамических и prerendering статических страниц.

Формулировка о «постоянной SPA-стратегии» сохранилась только как возможное прочтение
обзорной схемы `React + Vite SPA` и описания React Router как маршрутизатора SPA. Эти места
описывают текущее состояние MVP, но без контекста могут быть ошибочно восприняты как
production-решение. Если трактовать их как постоянное решение, они противоречат ТЗ.
Приоритет документов разрешает такое противоречие в пользу ТЗ, а настоящий ADR явно
фиксирует границу этапов.

Нужно сохранить следующие свойства текущего приложения:

- FSD-границы и публичные API модулей;
- единый Axios API client, Zod-валидацию и mapper-функции;
- доменные SEO-данные категорий и товаров;
- клиентскую локальную корзину без индексации;
- возможность локальной разработки с MSW;
- независимость UI от Axios, DTO и MSW;
- отсутствие browser-only действий во время импорта модулей и серверного рендера.

## Критерии выбора

1. Индексируемый HTML и уникальные метаданные без обязательного выполнения JavaScript.
2. Серверные статусы `200`, `404` и `500`.
3. Актуальность динамических категорий, товаров, цен и наличия.
4. Совместимость с React, Vite, React Router и существующими FSD-модулями.
5. Контролируемое кеширование и понятная инвалидация.
6. Независимость от конкретного hosting-провайдера.
7. Минимальная дополнительная инфраструктурная сложность.
8. Возможность оставить корзину полностью клиентской.

## Options

### 1. Сохранить SPA для публичного storefront

Преимущества:

- отсутствует миграционная работа;
- достаточно статического hosting и SPA fallback;
- сохраняется самый простой runtime.

Недостатки:

- маршрутный контент и метаданные появляются только после JavaScript;
- товар и категория не получают надёжный SEO HTML;
- отсутствующие сущности возвращаются как HTTP `200`;
- требования ТЗ к публичному запуску не выполняются.

Вариант допустим только для локального MVP, preview или закрытого staging.

### 2. Prerendering всех публичных маршрутов

Преимущества:

- быстрый статический HTML;
- простое CDN-кеширование;
- не требуется постоянный SSR runtime.

Недостатки:

- сборка должна заранее знать все категории и товары;
- рост каталога увеличивает время сборки;
- цены, наличие и архивность устаревают до следующей сборки;
- поиск, сортировка, пагинация и неизвестные slug требуют отдельной серверной логики;
- оперативное удаление товара требует rebuild и инвалидацию CDN.

Подходит статическим страницам, но не всему каталогу.

### 3. SSR всех маршрутов

Преимущества:

- единая модель выполнения;
- актуальный HTML и корректные статусы для динамических маршрутов;
- не требуется перечислять все slug во время сборки.

Недостатки:

- статические страницы получают ненужную runtime-зависимость;
- возрастают стоимость, latency и требования к доступности SSR runtime;
- требуется серверная политика кеширования для каждого запроса.

Вариант решает требования, но создаёт лишнюю сложность для неизменяемых страниц.

### 4. Собственный Vite SSR или другой совместимый runtime

Преимущества:

- полный контроль над серверным entrypoint и deployment artifact;
- возможность адаптации к конкретному runtime.

Недостатки:

- самостоятельно реализуются route data loading, статусы, error boundaries,
  metadata и prerender pipeline;
- больше проектного кода и долгосрочной поддержки;
- выше риск расхождения клиентской и серверной маршрутизации.

Этот путь допустим только если выбранный hosting не поддерживает React Router Framework
Mode и отдельный ADR обоснует замену.

### 5. React Router Framework Mode: SSR + prerendering

Преимущества:

- остаются React Router и Vite;
- route loaders, status responses, error boundaries и metadata имеют единый framework-путь;
- можно совместить SSR динамических и prerendering статических маршрутов;
- миграция локализуется в app/router и route entries без переноса бизнес-логики в страницы.

Недостатки:

- меняются entrypoints, сборка и формат deployment artifact;
- нужен совместимый server/edge runtime;
- серверным loaders потребуется абсолютный адрес backend или server-only proxy;
- необходимо проверить SSR-совместимость сторонних библиотек и гидратацию корзины.

## Decision

Перед публичным production-запуском перевести storefront на React Router Framework Mode и
использовать гибридный рендеринг:

- prerendering: `/`, `/contacts`, `/privacy`, `/terms`;
- SSR: `/catalog`, `/catalog/*`, `/product/:productSlug`;
- client-only после гидратации: `/cart`, с `noindex, nofollow`;
- dev-only: `/ui-preview`, без production route;
- неизвестные товар, категория и маршрут возвращают HTTP `404`;
- необработанная серверная ошибка возвращает HTTP `500` и безопасный error UI.

Данные SSR-загрузчиков должны проходить через существующие API-контракты, Zod-схемы и
mapper-функции. UI не должен получать доступ к Axios или DTO. Для server-side запросов
потребуется отдельный server-only API origin либо same-origin proxy; его нельзя оформлять
как `VITE_*` секрет.

Чистая функция `createPageMetadata` остаётся источником формирования метаданных. Способ их
применения подключается к route metadata API Framework Mode без дублирования SEO-логики в
компонентах.

Политика кеширования на первом шаге:

- hashed assets — длительный immutable cache;
- prerendered HTML — CDN cache с инвалидацией при deployment;
- SSR HTML категорий и товаров — по умолчанию `no-store` до согласования допустимой
  давности цен и наличия;
- `404` и `500` — не кешировать длительно;
- короткий shared cache или stale-while-revalidate разрешается только после определения
  SLA актуальности и механизма инвалидации.

MSW остаётся инструментом local/test. Browser worker не запускается и не входит в
production artifact. Для server loaders в тестах используется Node MSW либо тестовый API,
но route modules не импортируют handlers или fixtures.

## Consequences

Положительные последствия:

- выполняются SEO- и HTTP-требования ТЗ;
- категории и товары получают актуальный серверный HTML;
- статические страницы не зависят от SSR runtime на каждый запрос;
- текущие модели, API-сегменты, mapper-функции и FSD-границы сохраняются;
- hosting можно выбрать отдельно по измеримым runtime-требованиям.

Отрицательные последствия и ограничения:

- текущий `dist/` статической SPA не является финальным публичным production artifact;
- deployment должен поддерживать серверный runtime и статические assets;
- потребуется новая схема сборки, server-only конфигурация API и тесты HTTP-статусов;
- TanStack Query hydration и клиентская гидратация Zustand требуют отдельной проверки;
- переход нельзя выполнить только изменением CDN rewrite.

## Шаги миграции

1. Выбрать hosting/runtime по требованиям `docs/deployment-requirements.md`.
2. Создать отдельную миграционную ветку и включить React Router Framework Mode.
3. Перенести route entries в framework route modules, сохранив FSD-композицию.
4. Реализовать loaders для каталога, категории и товара через существующий API-слой.
5. Разделить публичную клиентскую и server-only конфигурацию backend origin.
6. Подключить metadata descriptor к framework metadata API.
7. Реализовать route error boundaries и ответы `200`, `404`, `500`.
8. Настроить prerendering статических маршрутов.
9. Добавить SSR/prerender contract, hydration и HTTP-status тесты.
10. Проверить кеширование, security headers, Core Web Vitals и rollback на staging.

## Release blocker

Публичный production-запуск заблокирован, пока отдельная миграционная задача не реализует
это решение и не подтвердит:

- серверный HTML для главной, каталога, категорий, товаров и информационных страниц;
- корректные HTTP `200`, `404`, `500`;
- отсутствие MSW в server/client production artifacts;
- рабочую гидратацию корзины;
- прохождение SEO, accessibility, E2E и rollback-проверок на staging.

Текущий SPA artifact можно использовать для локальной разработки, автоматических тестов и
закрытого preview, но нельзя объявлять готовым к публичному production-релизу.
