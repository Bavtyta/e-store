# 0. Technology Stack

## Цель

Настоящий документ определяет инженерные стандарты Frontend-разработки интернет-магазина.

Все правила, описанные далее, основаны на выбранном технологическом стеке. Документ не рассматривает альтернативные архитектуры (Next.js, Remix, Nuxt и др.) и не предлагает их без наличия архитектурного решения (ADR).

Любые рекомендации должны учитывать ограничения и преимущества выбранного стека.

---

## Технологический стек

### Основные технологии

- React
- TypeScript
- Vite
- React Router
- TanStack Query
- React Hook Form
- Axios
- Zod
- ESLint
- Prettier
- Vitest
- Playwright

---

## Почему выбран именно этот стек

### React

Используется как основная библиотека пользовательского интерфейса благодаря:

- зрелой экосистеме;
- высокой производительности;
- большому количеству готовых решений;
- широкому распространению на рынке.

---

### TypeScript

Используется для:

- статической типизации;
- уменьшения количества ошибок;
- безопасного рефакторинга;
- улучшения поддержки IDE.

---

### Vite

Используется как инструмент сборки благодаря:

- очень быстрому запуску Dev Server;
- высокой скорости HMR;
- современной системе сборки;
- небольшому количеству конфигурации.

---

### React Router

Используется для маршрутизации SPA-приложения.

Маршрутизация должна быть максимально простой и предсказуемой.

---

### TanStack Query

Используется как единственный источник управления Server State.

Преимущества:

- кэширование;
- повторные запросы;
- инвалидация;
- синхронизация состояния с сервером.

---

### React Hook Form

Используется для всех сложных пользовательских форм.

Самостоятельная реализация управления формами допускается только для простых случаев.

---

### Axios

Используется как единый HTTP-клиент проекта.

Использование fetch напрямую допускается только при наличии объективной причины.

---

### Zod

Используется для:

- валидации данных;
- проверки схем;
- безопасного преобразования данных API.

---

### ESLint

Используется для автоматического контроля качества кода.

---

### Prettier

Используется для автоматического форматирования.

Правила форматирования не обсуждаются во время Code Review.

---

### Vitest

Используется для Unit и Integration тестирования.

---

### Playwright

Используется для End-to-End тестирования критических пользовательских сценариев.

---

## Ограничения выбранного стека

При разработке необходимо учитывать особенности React + Vite.

Запрещается:

- предлагать переход на Next.js без оформления ADR;
- изменять архитектуру проекта ради использования возможностей других фреймворков;
- использовать библиотеки, несовместимые с React 19 и Vite.

Все рекомендации должны быть ориентированы на максимальное использование возможностей выбранного стека.

---

## Масштабирование проекта

Архитектура должна предусматривать возможность дальнейшего развития проекта без полного переписывания Frontend.

Проект должен поддерживать:

- рост количества страниц;
- увеличение каталога товаров;
- подключение авторизации;
- личный кабинет;
- мобильное приложение (через отдельный клиент);
- расширение функциональности интернет-магазина.

Frontend должен оставаться независимым от реализации Backend и взаимодействовать с ним исключительно через публичный API.



# 1. Purpose

## Назначение документа

Engineering Standards определяет единые правила разработки Frontend-приложения.

Документ предназначен для:

- обеспечения единого стиля разработки;
- снижения количества архитектурных ошибок;
- уменьшения технического долга;
- ускорения Code Review;
- упрощения сопровождения проекта;
- повышения качества продукта.

Настоящий документ является обязательным для всех участников Frontend-команды.

---

## Приоритет документа

При возникновении противоречий применяется следующий порядок приоритетов:

1. Требования бизнеса.
2. Product Requirements (TZ).
3. Engineering Standards.
4. ADR.
5. Личные предпочтения разработчиков.

Личные предпочтения не могут быть причиной нарушения Engineering Standards.

---

## Цели проекта

Frontend должен обеспечивать:

- высокую производительность;
- масштабируемость;
- безопасность;
- удобство сопровождения;
- предсказуемую архитектуру;
- качественный пользовательский опыт;
- высокий уровень SEO в рамках возможностей React + Vite.

---

## Что регулирует документ

Engineering Standards определяет:

- процесс разработки;
- архитектуру Frontend;
- правила организации кода;
- правила взаимодействия модулей;
- требования к безопасности;
- требования к тестированию;
- требования к производительности;
- правила проведения Code Review.

---

## Что документ не регулирует

Документ не определяет:

- бизнес-требования;
- дизайн интерфейсов;
- внутреннюю архитектуру Backend;
- процесс управления проектом;
- требования заказчика.

Эти вопросы регулируются отдельной документацией проекта.

---

## Изменение документа

Engineering Standards является развивающимся документом.

Изменения допускаются только при выполнении одного из условий:

- принято новое архитектурное решение (ADR);
- обнаружен недостаток существующих правил;
- изменился технологический стек;
- появились новые требования проекта.

Каждое изменение должно улучшать качество документа и не противоречить существующим принципам.




# 2. Architecture Principles

## Основной принцип

Архитектура проекта должна быть простой, понятной и предсказуемой.

Если существует несколько корректных решений, предпочтение всегда отдаётся более простому.

Сложность должна появляться только тогда, когда она действительно необходима.

---

## Приоритеты при принятии решений

При выборе архитектурного решения необходимо руководствоваться следующими приоритетами (от наиболее важного к менее важному):

1. Простота сопровождения.
2. Простота понимания.
3. Предсказуемость поведения.
4. Масштабируемость.
5. Безопасность.
6. Производительность.
7. Скорость разработки.

Если два решения функционально эквивалентны, предпочтение отдаётся более простому.

---

## Основные принципы

При разработке необходимо соблюдать следующие принципы:

- KISS (Keep It Simple, Stupid);
- DRY (Don't Repeat Yourself);
- SOLID (где применимо);
- Composition over Inheritance;
- YAGNI (You Aren't Gonna Need It);
- Single Source of Truth.

Любое отклонение должно быть обосновано.

---

## Принципы проектирования

Предпочитать:

- композицию наследованию;
- явный код неявному;
- небольшие специализированные компоненты универсальным;
- переиспользование существующего кода созданию нового;
- стандартные возможности React и TypeScript сторонним библиотекам.

---

## Управление сложностью

Новая абстракция должна появляться только при наличии нескольких независимых сценариев использования.

Не создавать универсальные решения «на будущее».

Любая дополнительная сложность должна приносить измеримую пользу.

---

## Масштабируемость

Каждое новое решение должно учитывать возможность развития проекта.

Добавление новой функциональности не должно требовать изменения большого количества существующего кода.

Изменения должны быть локализованы в пределах своей области ответственности.

---

## Связанность модулей

Модули должны быть максимально независимыми.

Не допускается создание скрытых зависимостей между Feature, Entity и Shared.

Каждый модуль взаимодействует с другими только через публичный API.

---

## Источник истины

Для каждого типа данных должен существовать только один источник истины.

Не допускается дублирование состояния между несколькими механизмами хранения.

---

## Преждевременная оптимизация

Запрещается усложнять архитектуру ради гипотетической производительности.

Любая оптимизация должна быть подтверждена измерениями или объективной необходимостью.

---

## Архитектурные изменения

Любое изменение, которое затрагивает структуру проекта, способ взаимодействия модулей или выбор технологий, должно сопровождаться ADR.












# 3. Development Process

## Цель

Процесс разработки должен обеспечивать:

- предсказуемость архитектурных решений;
- высокое качество кода;
- минимальное количество технического долга;
- быстрые code review;
- возможность масштабирования проекта без переписывания существующего кода.

При разработке предпочтение всегда отдается архитектурно правильному решению, а не самому быстрому.

---

## Принципы

Перед написанием кода разработчик должен понять задачу, а не сразу приступать к реализации.

Каждое изменение проходит одинаковый жизненный цикл:

1. Анализ задачи.
2. Проектирование решения.
3. Реализация.
4. Самопроверка.
5. Code Review.
6. Merge.

Запрещается пропускать этап анализа и сразу писать код.

---

## 3.1 Анализ задачи

Перед началом реализации необходимо ответить на следующие вопросы.

### Что необходимо реализовать?

Определить функциональные требования.

### Где должна находиться новая функциональность?

Определить слой FSD:

- app
- pages
- widgets
- features
- entities
- shared

### Можно ли использовать существующий код?

Перед созданием новых компонентов, хуков, утилит или сервисов необходимо проверить существующие реализации.

Дублирование функциональности запрещено.

### Какие могут возникнуть последствия?

Перед реализацией необходимо оценить влияние изменений на:

- архитектуру;
- производительность;
- безопасность;
- пользовательский опыт;
- масштабируемость.

Если изменение затрагивает несколько модулей или требует изменения архитектуры, необходимо создать ADR.

---

## 3.2 Проектирование решения

Перед написанием кода необходимо определить:

- какие компоненты будут созданы;
- какие сущности будут использоваться;
- где будет храниться состояние;
- каким образом будет происходить взаимодействие с API;
- какие данные являются серверными, а какие локальными.

Любое решение должно быть максимально простым.

Запрещается создавать абстракции без реальной необходимости.

Следовать принципу YAGNI.

---

## 3.3 Реализация

Во время разработки необходимо соблюдать следующие правила.

Каждый компонент должен иметь одну ответственность.

Каждая функция должна выполнять одну задачу.

Не создавать большие компоненты.

Не использовать `any`.

Не дублировать код.

Не использовать преждевременную оптимизацию.

Если код становится сложным для понимания, необходимо пересмотреть архитектурное решение.

---

## 3.4 Самопроверка

Перед созданием Pull Request разработчик обязан самостоятельно проверить изменения.

Чек-лист:

□ Код соответствует архитектуре проекта.

□ Нет дублирования.

□ Нет неиспользуемого кода.

□ Нет временных решений.

□ Все типы корректны.

□ Нет `console.log`.

□ Нет `TODO`, если они не оформлены как отдельные задачи.

□ Нет предупреждений линтера.

□ Нет ошибок TypeScript.

□ Все тесты проходят успешно.

---

## 3.5 Code Review

Цель Code Review — повышение качества проекта, а не поиск виноватых.

Во время ревью проверяется:

- архитектура;
- читаемость;
- соответствие FSD;
- производительность;
- безопасность;
- типизация;
- повторное использование существующего кода;
- соответствие Engineering Standards.

Замечания должны содержать объяснение причины, а не только указание на проблему.

---

## 3.6 Merge

Изменение может быть объединено только при выполнении всех условий:

- CI успешно завершился;
- отсутствуют ошибки линтера;
- отсутствуют ошибки TypeScript;
- все обязательные замечания Code Review устранены;
- Pull Request одобрен.

## Масштаб изменений

Перед началом реализации необходимо определить масштаб задачи.

### Малое изменение

Исправление ошибки.

Небольшой рефакторинг.

Изменение существующего UI.

ADR не требуется.

---

### Среднее изменение

Новая Feature.

Изменение API.

Добавление нового состояния.

Допускается краткое описание решения в Pull Request.

---

### Крупное изменение

Изменение архитектуры.

Новый модуль.

Новая подсистема.

Изменение структуры проекта.

Перед началом реализации необходимо создать ADR.


## Принятие решений

Если существует несколько возможных вариантов реализации, необходимо выбирать тот, который:

1. проще поддерживать;
2. легче тестировать;
3. требует меньшего количества связей между модулями;
4. соответствует архитектуре проекта;
5. не создает технический долг.

Если более простое решение удовлетворяет всем требованиям, оно должно быть предпочтительнее более сложного.





# 4. Component Design Rules

## Цель

Настоящий раздел определяет правила размещения кода в архитектуре проекта.

Любой разработчик должен иметь возможность определить место новой функциональности без обсуждений и субъективных решений.

Если правило не позволяет однозначно определить слой — правило должно быть изменено.

---

# Главный принцип

Размещать код необходимо исходя не из его размера, а из ответственности.

Не существует правила:

> "маленький компонент → Shared"

или

> "большой компонент → Widget"

Единственный критерий — ответственность компонента.

---

# app

Содержит только код инициализации приложения.

Допустимо:

- роутинг;
- глобальные провайдеры;
- тема;
- конфигурация приложения;
- Error Boundary;
- Layout верхнего уровня.

Запрещено:

- бизнес-логика;
- API;
- работа с товарами;
- UI каталога;
- пользовательские сценарии.

---

# pages

Каждая папка pages соответствует одному маршруту приложения.

Page отвечает только за композицию страницы.

Page не должна содержать бизнес-логику.

Page собирает:

- Widgets
- Features
- Entities

Page практически никогда не содержит собственный UI.

---

# widgets

Widget объединяет несколько Feature или Entity для реализации законченного блока страницы.

Примеры:

Каталог товаров

Шапка сайта

Футер

Корзина в боковой панели

Секция "Популярные товары"

Widget не должен содержать бизнес-логику.

Widget отвечает только за композицию.

---

# features

Feature реализует одно пользовательское действие.

Главный вопрос:

"Что делает пользователь?"

Если можно ответить одним глаголом —

скорее всего это Feature.

Примеры:

Добавить товар в корзину

Добавить в избранное

Авторизация

Регистрация

Поиск

Фильтрация

Сортировка

Оформление заказа

Изменение профиля

Удаление адреса

Feature может содержать:

- UI
- Model
- API
- Lib

Feature запрещено использовать напрямую внутри другой Feature.

Взаимодействие осуществляется через публичный API.

---

# entities

Entity описывает бизнес-сущность.

Entity отвечает на вопрос:

"Что существует в предметной области?"

Примеры:

Product

Category

Order

User

Cart

Favorite

Entity содержит:

- модель
- типы
- API
- UI отображения сущности
- форматирование

Entity не содержит пользовательских сценариев.

Например:

ProductCard

может находиться в Entity,

но кнопка

"Добавить в корзину"

не относится к Entity.

Она относится к Feature.

---

# shared

Shared содержит инфраструктуру проекта.

Допустимо:

UI Kit

иконки

утилиты

валидация

константы

axios

конфигурация

хуки общего назначения

lib

Запрещено помещать в Shared бизнес-логику.

Если код знает что такое Product —

это уже не Shared.

---

# Component Responsibilities

Компонент должен иметь одну ответственность.

Если компонент одновременно:

- загружает данные;
- содержит бизнес-логику;
- отвечает за отображение;

необходимо разделить его минимум на два компонента.

Исключение допускается только при очевидном усложнении архитектуры.

---

# Component Size

Размер компонента сам по себе не является причиной рефакторинга.

Причиной является количество ответственностей.

Большой компонент с одной ответственностью предпочтительнее нескольких искусственно разделенных компонентов.

---

# Composition

Предпочитать композицию наследованию.

Предпочитать маленькие специализированные компоненты универсальным компонентам.

Создавать универсальные компоненты только после появления минимум двух независимых сценариев использования.

Запрещается создавать абстракции "на будущее".

Следовать принципу YAGNI.

---

# Public API

Каждый Feature, Entity и Widget должен иметь публичный API.

Внешний код не должен импортировать внутренние файлы напрямую.

Допустимы импорты только через index.ts.

Это позволяет изменять внутреннюю структуру без влияния на остальной проект.

---

# Custom Hooks

Создавать Custom Hook необходимо если:

- логика используется более одного раза;
- логика усложняет компонент;
- требуется повторное использование.

Не создавать Hook ради нескольких строк кода.

Custom Hook должен инкапсулировать поведение, а не просто группировать функции.

---

# Providers

Provider допускается создавать только если состояние действительно должно быть глобальным.

Не использовать Provider вместо обычного компонента.

Избыточное количество Provider усложняет дерево приложения.

---

# Anti-patterns

Запрещается:

❌ Feature ради одной кнопки.

❌ Widget из одного компонента.

❌ Shared, знающий о бизнес-сущностях.

❌ Entity, содержащая пользовательские сценарии.

❌ Page с бизнес-логикой.

❌ Огромные универсальные компоненты.

❌ Универсальные компоненты "на будущее".

❌ Prop Drilling глубже двух уровней без веской причины.

❌ Использование Context вместо более подходящего инструмента.



# 5. State Management

## Цель

Настоящий раздел определяет правила выбора инструмента для хранения состояния.

Главный принцип:

Каждый тип состояния должен храниться в инструменте, предназначенном именно для него.

Использование одного инструмента для всех типов состояния запрещается.

---

## Классификация состояния

В проекте используются следующие виды состояния:

1. Server State
2. UI State
3. Form State
4. URL State
5. Local Component State
6. Derived State

Каждый тип имеет собственные правила хранения.

---

# Server State

Server State — это данные, источником истины которых является сервер.

Примеры:

- список товаров;
- карточка товара;
- категории;
- результаты поиска;
- история заказов;
- пользовательский профиль;
- адреса доставки.

Для Server State используется только TanStack Query.

Запрещается:

- хранить Server State в Context;
- хранить Server State в Zustand;
- копировать данные Query в локальный state без необходимости.

Исключения допускаются только при наличии документированного архитектурного решения (ADR).

---

# UI State

UI State описывает только текущее состояние интерфейса.

Примеры:

- открыто ли модальное окно;
- выбран ли таб;
- открыто ли меню;
- активен ли Sidebar;
- текущая тема оформления.

Использовать:

- useState;
- Context (если состояние действительно глобальное);
- Zustand (если требуется совместное использование между независимыми частями интерфейса).

Запрещается хранить UI State в TanStack Query.

---

# Form State

Form State отвечает за ввод пользователя.

Примеры:

- оформление заказа;
- фильтры;
- авторизация;
- регистрация;
- изменение профиля.

Использовать React Hook Form.

Запрещается реализовывать управление сложными формами вручную через useState.

---

# URL State

URL должен быть источником истины для состояния, которое должно сохраняться при обновлении страницы или быть доступным по ссылке.

Примеры:

- поисковый запрос;
- сортировка;
- фильтры;
- номер страницы;
- категория.

Использовать search params.

Запрещается хранить такие данные только в локальном состоянии.

---

# Local Component State

Если состояние используется только внутри одного компонента, применять useState.

Не выносить локальное состояние в глобальные хранилища без объективной необходимости.

---

# Derived State

Derived State — это данные, вычисляемые из других данных.

Примеры:

- итоговая стоимость корзины;
- количество товаров;
- сгруппированные категории.

Не хранить Derived State в отдельном состоянии.

Использовать вычисления (`useMemo` только при подтвержденной необходимости).

---

# Context

Context используется только для действительно глобальных данных.

Допустимо:

- тема оформления;
- язык интерфейса;
- настройки приложения.

Не использовать Context как универсальное хранилище состояния.

---

# Zustand

Использовать Zustand только для сложного клиентского состояния, которое:

- разделяется между несколькими независимыми компонентами;
- не является Server State;
- не подходит для Context.

Примеры:

- состояние корзины (если до синхронизации с сервером);
- глобальные настройки интерфейса;
- мастер оформления заказа.

---

# TanStack Query

TanStack Query используется исключительно для взаимодействия с сервером.

Query отвечает за:

- получение данных;
- кэширование;
- повторные запросы;
- инвалидацию;
- синхронизацию.

Запрещается использовать Query Cache как глобальное хранилище приложения.

---

# useMemo

Не использовать useMemo "на всякий случай".

Мемоизация применяется только после подтверждения необходимости (профилирование, измерения, очевидно дорогие вычисления).

Преждевременная оптимизация запрещается.

---

# useCallback

Использовать только если:

- функция передается в мемоизированный компонент;
- функция используется как зависимость другого Hook;
- это подтверждено профилированием.

Не использовать useCallback ради соответствия стилю.

---

# React.memo

Использовать только для компонентов, которые:

- часто перерисовываются;
- имеют дорогой рендер;
- получают стабильные props.

Не оборачивать все компоненты подряд.

---

# Decision Rules

Перед выбором инструмента ответить на вопросы:

Данные приходят с сервера?

→ TanStack Query.

---

Состояние относится только к одному компоненту?

→ useState.

---

Нужно сохранить состояние в URL?

→ Search Params.

---

Это форма?

→ React Hook Form.

---

Это вычисляемые данные?

→ Derived State.

---

Это действительно глобальное состояние приложения?

→ Context или Zustand.

---

# Anti-patterns

Запрещается:

❌ Использовать Context вместо TanStack Query.

❌ Копировать Server State в локальный state.

❌ Хранить фильтры только в Zustand.

❌ Использовать useEffect для вычислений.

❌ Использовать useMemo без причины.

❌ Использовать useCallback без причины.

❌ Хранить производные данные в state.

❌ Создавать несколько источников истины для одного состояния.




# 6. Error Handling

## Цель

Обработка ошибок должна быть единообразной во всем приложении.

Пользователь должен получать понятную обратную связь, а разработчик — возможность быстро определить причину проблемы.

Ошибки не должны обрабатываться произвольно в каждом компоненте.

---

# Основные принципы

Источник истины об ошибке — Backend.

Frontend отвечает за:

- корректное отображение ошибки;
- сохранение состояния интерфейса;
- возможность повторного действия;
- логирование (при необходимости).

Frontend не должен самостоятельно интерпретировать бизнес-ошибки.

---

# Классификация ошибок

В проекте используются следующие категории ошибок:

- Network Error
- Validation Error
- Authentication Error
- Authorization Error
- Business Error
- Server Error
- Unknown Error

Каждая категория имеет собственные правила обработки.

---

# Network Error

Причины:

- отсутствие сети;
- timeout;
- DNS;
- сервер недоступен.

Поведение:

- показать сообщение пользователю;
- сохранить введённые данные;
- предоставить кнопку "Повторить";
- не очищать интерфейс без необходимости.

---

# Validation Error

Ошибки проверки пользовательского ввода.

Например:

- неверный email;
- пустое обязательное поле;
- неправильный формат телефона.

Отображаются непосредственно рядом с соответствующим полем.

Не использовать toast для ошибок валидации формы.

---

# Authentication Error (401)

Причина:

Пользователь не авторизован.

Поведение:

- перенаправить на страницу авторизации (если она существует);
- сохранить URL для возврата;
- очистить устаревшие данные пользователя.

---

# Authorization Error (403)

Причина:

Недостаточно прав.

Поведение:

- показать страницу или блок "Недостаточно прав";
- не выполнять повторные запросы автоматически.

---

# Not Found (404)

Для API:

Показать Empty State.

Не использовать всплывающие уведомления.

Для маршрутов:

Отображать страницу 404.

---

# Conflict (409)

Используется при конфликте данных.

Например:

- товар закончился;
- данные были изменены;
- заказ уже обработан.

Поведение:

- показать понятное сообщение;
- предложить обновить данные.

---

# Validation Failed (422)

Backend возвращает ошибки полей.

Необходимо:

- сопоставить ошибки с соответствующими полями формы;
- автоматически установить ошибки через React Hook Form.

Запрещается отображать такие ошибки только в toast.

---

# Server Error (500)

Причина:

Ошибка сервера.

Поведение:

- показать экран ошибки или уведомление;
- предоставить возможность повторить действие;
- не показывать внутренние сообщения сервера пользователю.

---

# Unknown Error

Если тип ошибки определить невозможно:

- показать универсальное сообщение;
- записать информацию в лог (если подключено логирование);
- не раскрывать технические детали пользователю.

---

# Error Mapping

Все ошибки API должны проходить через единый слой преобразования.

Запрещается анализировать HTTP-статусы непосредственно внутри компонентов.

Правильно:

API → Error Mapper → UI

Неправильно:

Компонент → if (status === 404)

---

# User Messages

Все сообщения об ошибках должны быть:

- понятными;
- краткими;
- без технических терминов;
- без стеков вызовов;
- без внутренних кодов.

Плохо:

"Internal Server Error"

Хорошо:

"Не удалось загрузить товары. Попробуйте ещё раз."

---

# Retry Strategy

Автоматический повтор допускается только для временных ошибок сети.

Не повторять автоматически:

- 400
- 401
- 403
- 404
- 409
- 422

Повтор допустим для:

- timeout;
- 500;
- временных ошибок соединения.

Количество повторов определяется настройками TanStack Query.

---

# Error Boundary

Каждое приложение должно иметь глобальный Error Boundary.

Error Boundary отвечает только за ошибки рендера React.

Он не заменяет обработку ошибок API.

---

# Toast Notifications

Toast использовать только для:

- успешных действий;
- кратких уведомлений;
- неожиданных ошибок.

Не использовать toast:

- для ошибок валидации;
- для ошибок 404;
- для длительного отображения информации.

---

# Logging

Frontend не должен логировать персональные данные пользователя.

Запрещается выводить:

- токены;
- cookies;
- адреса;
- телефоны;
- email;
- персональные данные.

В production запрещается оставлять console.log.

---

# Anti-patterns

Запрещается:

❌ Проверять HTTP-статусы внутри компонентов.

❌ Показывать пользователю сообщения сервера без обработки.

❌ Использовать toast для ошибок формы.

❌ Игнорировать ошибки Promise.

❌ Скрывать ошибки через пустой catch.

❌ Дублировать обработку одинаковых ошибок в нескольких местах.

❌ Раскрывать внутренние детали реализации Backend.




# 7. Security

## Цель

Настоящий раздел определяет требования безопасности Frontend-приложения.

Безопасность развивается по этапам проекта.

Каждый этап содержит только актуальные требования.

Настоящий документ описывает **Stage A** — каталог интернет-магазина без авторизации, личного кабинета и онлайн-оплаты.

При переходе к следующим этапам требования расширяются, но не изменяют существующие правила.

---

# Основные принципы

Frontend не является доверенной средой.

Любые данные, полученные:

- от пользователя;
- из URL;
- из API;
- из LocalStorage;
- из SessionStorage;

считаются недоверенными.

Источник истины всегда Backend.

Frontend выполняет проверки только для улучшения пользовательского опыта (UX), но не обеспечивает безопасность данных.

---

# Работа с пользовательским вводом

Любой пользовательский ввод должен проходить валидацию.

Валидация на клиенте предназначена исключительно для удобства пользователя.

Запрещается считать клиентскую валидацию механизмом защиты.

Любые ограничения должны дублироваться на сервере.

---

# Работа с HTML

Использование dangerouslySetInnerHTML запрещено.

Исключение допускается только при соблюдении всех условий:

- источник HTML полностью доверенный;
- HTML предварительно очищен (sanitized);
- решение документировано.

Во всех остальных случаях отображать текст как обычную строку.

---

# Работа со ссылками

Все внешние ссылки должны использовать:

rel="noopener noreferrer"

при открытии в новой вкладке.

Запрещается использовать target="_blank" без rel.

Если URL формируется динамически, необходимо проверять допустимый протокол.

Допустимые протоколы:

- https:
- mailto:
- tel:

Запрещено:

- javascript:
- data: (кроме заранее определённых сценариев)
- неизвестные схемы.

---

# Работа с изображениями

URL изображений считается недоверенным.

Frontend не должен:

- выполнять изображения как код;
- интерпретировать SVG как HTML;
- вставлять SVG через dangerouslySetInnerHTML.

При использовании пользовательских изображений необходимо отдавать предпочтение обычному тегу `<img>` или безопасным компонентам.

---

# Работа с данными API

Frontend не должен:

- предполагать корректность данных;
- доверять обязательности полей;
- полагаться на порядок элементов массива.

Ответы API должны проходить через слой типизации и преобразования.

Некорректные данные должны обрабатываться безопасно без падения приложения.

---

# Работа с LocalStorage

LocalStorage используется только для некритичных данных.

Допустимо:

- тема оформления;
- язык;
- пользовательские настройки;
- состояние интерфейса.

Запрещается хранить:

- access token;
- refresh token;
- персональные данные;
- платежную информацию.

---

# Content Security Policy

Приложение должно поддерживать работу с CSP.

При разработке запрещается использовать решения, несовместимые с Content Security Policy.

Не использовать:

- inline script;
- eval();
- new Function().

Любая необходимость использования подобных механизмов должна быть отдельно согласована.

---

# Зависимости

Использовать только поддерживаемые библиотеки.

Перед добавлением новой зависимости необходимо ответить на вопросы:

- существует ли активная поддержка;
- есть ли критические уязвимости;
- действительно ли библиотека необходима.

Запрещается добавлять библиотеку ради нескольких строк кода.

---

# Проверка зависимостей

Проект должен регулярно проверяться средствами:

- npm audit;
- Dependabot (или аналогичным инструментом);
- GitHub Security Alerts.

Критические уязвимости должны устраняться до релиза.

---

# Environment Variables

Frontend не является безопасным местом хранения секретов.

Переменные окружения Vite (`VITE_*`) считаются публичными.

Запрещается помещать в них:

- API-ключи с привилегиями;
- секретные токены;
- пароли;
- приватные сертификаты.

Все секреты должны храниться только на Backend.

---

# Console

В production запрещается оставлять:

- console.log;
- console.debug;
- console.trace.

Допускается использование только централизованного механизма логирования ошибок (если он внедрен).

---

# Code Review Checklist

При ревью необходимо проверить:

□ Не используется dangerouslySetInnerHTML.

□ Нет inline script.

□ Нет eval().

□ Нет хранения чувствительных данных в LocalStorage.

□ Все внешние ссылки используют rel="noopener noreferrer".

□ Новые зависимости обоснованы.

□ Нет console.log.

□ Нет раскрытия внутренних ошибок Backend пользователю.

---

# Stage B (будущее)

После появления авторизации раздел будет дополнен:

- JWT;
- Refresh Token;
- Cookies;
- CSRF;
- RBAC;
- Route Guards.

---

# Stage C (будущее)

После подключения оплаты раздел будет дополнен:

- Webhook Verification;
- Replay Protection;
- PCI DSS;
- Работа с платежными провайдерами.






# 8. Performance

## Цель

Производительность должна достигаться за счет правильной архитектуры, а не большого количества локальных оптимизаций.

Преждевременная оптимизация запрещается.

Каждая оптимизация должна быть обоснована измерениями, профилированием или очевидной необходимостью.

---

# Основные принципы

Приоритеты производительности:

1. Правильная архитектура.
2. Минимальный объём JavaScript.
3. Быстрая загрузка страницы.
4. Минимальное количество повторных запросов.
5. Минимальное количество повторных рендеров.
6. Локальные оптимизации.

Не допускается усложнение архитектуры ради гипотетического прироста производительности.

---

# Core Web Vitals

При разработке необходимо учитывать:

- LCP (Largest Contentful Paint)
- INP (Interaction to Next Paint)
- CLS (Cumulative Layout Shift)

Любое изменение, способное ухудшить эти показатели, должно быть обосновано.

---

# Bundle Size

Перед добавлением новой библиотеки необходимо проверить:

- размер библиотеки;
- возможность tree-shaking;
- необходимость зависимости;
- наличие более лёгкой альтернативы.

Не использовать тяжёлые библиотеки ради одной функции.

Предпочитать встроенные возможности платформы и небольшие специализированные библиотеки.

---

# Code Splitting

Использовать динамический импорт (`React.lazy`) для:

- страниц;
- крупных модулей;
- редко используемых компонентов;
- административных разделов.

Не использовать lazy для небольших компонентов, которые всегда отображаются вместе со страницей.

---

# Data Fetching

Не выполнять повторные запросы без необходимости.

Использовать возможности TanStack Query:

- cache;
- staleTime;
- gcTime;
- prefetch;
- invalidateQueries.

Не выполнять запросы вручную через useEffect.

---

# Images

Все изображения должны:

- иметь корректные размеры;
- использовать современные форматы (WebP или AVIF при возможности);
- загружаться лениво (`loading="lazy"`), если находятся вне первого экрана;
- содержать атрибут `alt`.

Не загружать изображения большего размера, чем требуется для отображения.

---

# Rendering

Избегать лишних повторных рендеров.

Перед оптимизацией определить причину ререндера через React DevTools Profiler.

Не применять оптимизации "на всякий случай".

---

# React.memo

Использовать только если:

- компонент часто перерисовывается;
- рендер дорогой;
- props остаются стабильными.

Не оборачивать все компоненты подряд.

---

# useMemo

Использовать только для:

- дорогих вычислений;
- сохранения ссылочной стабильности, когда это действительно необходимо.

Не использовать useMemo для простых операций.

---

# useCallback

Использовать только если:

- функция передается в memo-компонент;
- используется как зависимость другого Hook;
- это подтверждено профилированием.

---

# Virtualization

Использовать виртуализацию списков только если количество одновременно отображаемых элементов действительно велико.

Для каталога решение принимается на основании требований продукта и результатов измерений.

Не применять виртуализацию без необходимости.

---

# Pagination

Большие наборы данных должны загружаться постранично.

Не загружать весь каталог товаров одним запросом.

---

# Infinite Scroll

Использовать только если это улучшает пользовательский сценарий.

Для B2B-магазина по умолчанию предпочтительнее классическая пагинация.

Если используется Infinite Scroll, пользователь должен иметь возможность быстро вернуться к началу списка и сохранить позицию при возврате.

---

# Search

Поиск должен использовать debounce.

Не выполнять запрос после каждого символа.

Значение debounce определяется требованиями продукта и пользовательским опытом.

---

# Filtering

Фильтрация должна выполняться на сервере, если объём данных может существенно увеличиться.

Не переносить большие выборки на клиент ради локальной фильтрации.

---

# Caching

Использовать кэширование только для данных, которые действительно используются повторно.

Настройки TanStack Query должны учитывать:

- частоту изменения данных;
- стоимость повторного запроса;
- требования актуальности.

---

# Decision Rules

Перед оптимизацией необходимо ответить на вопросы:

Проблема подтверждена измерениями?

↓

Да → оптимизировать.

↓

Нет → оставить код простым.

---

Можно уменьшить Bundle без ухудшения архитектуры?

↓

Да → уменьшить.

---

Компонент действительно дорогой?

↓

Да → рассмотреть React.memo.

---

Данные используются повторно?

↓

Да → использовать кэширование.

---

# Code Review Checklist

При ревью необходимо проверить:

□ Нет преждевременной оптимизации.

□ Нет необоснованного useMemo.

□ Нет необоснованного useCallback.

□ Нет React.memo без причины.

□ Изображения оптимизированы.

□ Используется lazy loading там, где это оправдано.

□ Нет повторных запросов.

□ Не загружается лишний объём данных.

□ Не увеличен размер bundle без необходимости.

---

# Anti-patterns

Запрещается:

❌ Оптимизировать без измерений.

❌ Использовать useMemo "для красоты".

❌ Использовать useCallback "по привычке".

❌ Загружать весь каталог сразу.

❌ Выполнять поиск после каждого символа.

❌ Фильтровать большие объёмы данных только на клиенте.

❌ Использовать виртуализацию без необходимости.

❌ Добавлять тяжёлые библиотеки ради одной функции.




# 9. Testing Policy

## Цель

Тестирование должно подтверждать корректность поведения приложения, а не особенности его реализации.

Главная цель тестов — предотвращение регрессий при изменении кода.

Тесты являются частью продукта и должны сопровождаться так же, как и основной код.

---

# Основные принципы

Приоритет тестирования:

1. Поведение пользователя.
2. Бизнес-логика.
3. Контракты.
4. Взаимодействие модулей.

Не тестировать внутреннюю реализацию компонентов.

Тест должен отвечать на вопрос:

"Работает ли функция так, как ожидает пользователь?"

а не

"Как именно реализован компонент?"

---

# Что тестируется обязательно

Обязательному тестированию подлежат:

- бизнес-логика;
- утилиты;
- преобразование данных;
- мапперы;
- пользовательские сценарии;
- работа с API (через моки);
- обработка ошибок;
- критические пути оформления заказа;
- навигация.

---

# Что допускается не тестировать

Допускается отсутствие отдельных тестов для:

- простых Presentational Components;
- SVG;
- иконок;
- констант;
- примитивных компонентов UI Kit;
- простых Layout-компонентов.

Если компонент практически не содержит логики, отдельный тест не обязателен.

---

# Что запрещается тестировать

Запрещается писать тесты, проверяющие:

- внутреннее состояние React;
- private-функции;
- реализацию сторонних библиотек;
- CSS-классы (если они не влияют на поведение);
- количество вызовов useState/useEffect;
- внутреннюю структуру компонентов.

Тест должен оставаться корректным после рефакторинга без изменения поведения.

---

# Unit Tests

Unit Test проверяет одну независимую единицу логики.

Подходящие кандидаты:

- formatter;
- parser;
- mapper;
- validator;
- calculator;
- helper;
- utility.

Unit Test должен быть:

- быстрым;
- независимым;
- воспроизводимым.

---

# Component Tests

Проверяют поведение компонента.

Необходимо проверять:

- корректный рендер;
- взаимодействие пользователя;
- отображение ошибок;
- состояния загрузки;
- пустые состояния.

Не проверять внутреннюю реализацию.

---

# Integration Tests

Проверяют взаимодействие нескольких модулей.

Например:

Feature

↓

Entity

↓

API

↓

UI

Интеграционный тест должен подтверждать, что модули корректно работают совместно.

---

# E2E

E2E покрывает только критические пользовательские сценарии.

Например:

- открытие каталога;
- поиск товара;
- применение фильтра;
- сортировка;
- просмотр карточки;
- добавление в корзину;
- оформление заказа;
- просмотр истории заказов (после появления авторизации).

Не использовать E2E вместо Unit Test.

---

# Contract Testing

Frontend должен проверять соответствие контракту API.

При изменении OpenAPI необходимо обновлять типы и связанные тесты.

Изменение API без обновления клиента не допускается.

---

# Test Data

Тестовые данные должны быть:

- небольшими;
- понятными;
- воспроизводимыми.

Не использовать случайные данные без необходимости.

Предпочитать фабрики (Factory) или Builder-паттерн для создания тестовых объектов.

---

# Mocks

Мокировать следует только внешние зависимости.

Допустимо:

- HTTP;
- Browser API;
- LocalStorage;
- Time.

Не мокировать собственную бизнес-логику без необходимости.

---

# Naming

Название теста должно описывать ожидаемое поведение.

Хорошо:

✓ should add product to cart

✓ displays empty state when no products found

Плохо:

✗ testProduct

✗ component works

---

# Regression

Каждая исправленная ошибка должна сопровождаться тестом, предотвращающим её повторное появление.

Если ошибка не может быть покрыта тестом, причина должна быть документирована.

---

# Definition of Done

Задача считается завершённой только если:

- реализована функциональность;
- обновлены существующие тесты;
- добавлены новые тесты при необходимости;
- все тесты успешно проходят;
- не снижается качество существующего покрытия.

---

# Code Review Checklist

Во время ревью проверить:

□ Тестируется поведение, а не реализация.

□ Нет избыточных моков.

□ Нет дублирования тестов.

□ Названия тестов понятны.

□ Добавлен regression test при исправлении бага.

□ Тесты независимы друг от друга.

□ Нет случайных падений (Flaky Tests).

---

# Anti-patterns

Запрещается:

❌ Тестировать private-методы.

❌ Проверять внутренний state React.

❌ Использовать snapshot как основной способ тестирования.

❌ Создавать тесты, зависящие от порядка выполнения.

❌ Использовать реальные HTTP-запросы в Unit Test.

❌ Дублировать проверки в нескольких тестах.

❌ Игнорировать нестабильные (Flaky) тесты вместо их исправления.





# 10. Git Workflow

## Цель

Git Workflow должен обеспечивать:

- простую и понятную историю изменений;
- минимальное количество конфликтов;
- безопасный процесс слияния;
- быстрые Code Review.

Для проекта используется **GitHub Flow**.

GitFlow не используется.

---

# Основные принципы

Главная ветка проекта всегда должна быть готова к развертыванию.

Разработка ведётся только в отдельных ветках.

Прямые коммиты в `main` запрещены.

---

# Структура веток

Используются следующие типы веток:

feature/
Используется для новой функциональности.

bugfix/
Используется для исправления ошибок.

hotfix/
Используется только для срочных исправлений после релиза.

chore/
Изменения инфраструктуры, зависимостей, конфигурации.

docs/
Изменения документации.

refactor/
Изменения внутренней структуры кода без изменения поведения.

---

Примеры

feature/catalog-search

feature/product-page

feature/cart

bugfix/filter-reset

hotfix/order-crash

docs/api

---

# Жизненный цикл задачи

1. Создать ветку от main.

↓

2. Выполнить разработку.

↓

3. Проверить локально.

↓

4. Создать Pull Request.

↓

5. Code Review.

↓

6. Исправить замечания.

↓

7. Merge.

---

# Pull Request

Каждая задача оформляется отдельным Pull Request.

Не объединять несколько независимых задач в одном PR.

Если задача становится слишком большой, её следует разделить.

---

# Размер Pull Request

Рекомендуемый размер:

до 400 изменённых строк.

Допустимо:

до 700 строк.

Если PR значительно больше, разработчик должен обосновать невозможность разделения.

Большие PR значительно усложняют ревью.

---

# Draft Pull Request

Использовать Draft PR если:

- работа ещё продолжается;
- требуется обсуждение архитектуры;
- нужен ранний фидбек.

Не создавать Draft только ради хранения кода.

---

# Code Review

Минимум один разработчик должен проверить Pull Request.

Во время ревью проверяется:

- архитектура;
- соответствие Engineering Standards;
- читаемость;
- безопасность;
- производительность;
- типизация;
- тесты.

Замечания должны быть конструктивными.

---

# Merge Strategy

Использовать Squash Merge.

Каждый Pull Request должен превращаться в один логически завершённый коммит.

Это обеспечивает понятную историю проекта.

---

# Обновление ветки

Перед Merge необходимо синхронизировать ветку с main.

Предпочтительно использовать Rebase.

Использование Merge Commit допускается только при наличии объективной причины.

---

# Conventional Commits

Использовать следующие типы:

feat:

Новая функциональность.

fix:

Исправление ошибки.

refactor:

Рефакторинг без изменения поведения.

docs:

Документация.

test:

Тесты.

style:

Изменения форматирования.

build:

Изменения сборки.

ci:

Изменения CI/CD.

chore:

Прочие изменения.

---

Примеры

feat: add product search

fix: resolve cart synchronization issue

docs: update engineering standards

refactor: simplify catalog filters

---

# Commit Messages

Коммит должен описывать:

что изменилось,

а не

что разработчик делал.

Хорошо

feat: add category filtering

Плохо

fix

update

changes

new code

---

# CI

Pull Request не может быть объединён если:

- не прошёл линтер;
- есть ошибки TypeScript;
- не прошли тесты;
- сборка завершилась с ошибкой.

---

# Merge Requirements

Merge допускается только если:

□ CI успешно завершился.

□ Получено необходимое количество Approve.

□ Все замечания устранены.

□ Нет конфликтов.

□ Нет незакоммиченных изменений.

□ Обновлена документация (если требуется).

---

# Работа с конфликтами

Конфликты должен разрешать автор Pull Request.

После разрешения конфликтов необходимо повторно проверить:

- сборку;
- тесты;
- линтер.

---

# Запрещается

❌ Push напрямую в main.

❌ Force Push в main.

❌ Merge без Code Review.

❌ Объединять несколько задач в одном PR.

❌ Создавать огромные Pull Request.

❌ Игнорировать замечания ревью без обсуждения.

❌ Использовать бессмысленные сообщения коммитов.

❌ Отключать проверки CI ради Merge.


# Definition of Ready

Перед началом разработки должно быть понятно:

□ Что нужно сделать.

□ Какой ожидается результат.

□ Какие API используются.

□ Есть ли дизайн.

□ Какие сценарии необходимо протестировать.

□ Есть ли открытые архитектурные вопросы.


# 11. Architectural Decision Records (ADR)

## Цель

ADR (Architectural Decision Record) используется для фиксации важных архитектурных решений проекта.

Главная задача ADR — сохранить контекст принятия решения, чтобы любой участник команды мог понять:

- какая проблема решалась;
- какие варианты рассматривались;
- почему был выбран именно этот вариант;
- какие последствия это решение имеет для проекта.

ADR является источником истины для архитектурных решений.

---

# Когда необходимо создавать ADR

ADR создаётся только для долгосрочных архитектурных решений.

Например:

- выбор архитектурного паттерна;
- выбор библиотеки;
- изменение структуры проекта;
- изменение схемы хранения состояния;
- стратегия взаимодействия с API;
- система авторизации;
- кэширование;
- SEO-стратегия;
- система логирования.

---

ADR не требуется для:

- исправления багов;
- небольшого рефакторинга;
- изменения UI;
- изменения текста;
- переименования компонентов.

---

# Когда создавать ADR

ADR необходимо создать до начала реализации.

Если решение уже принято и код написан, ADR оформляется только в исключительных случаях.

---

# Правила

Один ADR описывает одно решение.

Не объединять несколько независимых решений в одном документе.

Если проблема изменилась — создаётся новый ADR.

Старые ADR не переписываются.

При изменении решения старый ADR переводится в статус "Superseded".

---

# Статусы ADR

Каждый ADR должен иметь один из статусов:

Proposed

Решение обсуждается.

Accepted

Решение принято.

Rejected

Решение отклонено.

Superseded

Решение заменено новым ADR.

Deprecated

Решение больше не используется.

---

# Структура ADR

Каждый ADR должен содержать следующие разделы:

## Title

Краткое название решения.

---

## Status

Текущий статус ADR.

---

## Context

Описание проблемы.

Почему возникла необходимость принимать решение?

Какие ограничения существуют?

---

## Options

Какие варианты были рассмотрены.

Для каждого варианта необходимо кратко описать:

- преимущества;
- недостатки.

---

## Decision

Какое решение принято.

---

## Consequences

Какие последствия имеет решение.

Положительные.

Отрицательные.

Ограничения.

---

# Пример

Title

Использование TanStack Query

Status

Accepted

Context

Необходимо выбрать инструмент для работы с Server State.

Options

- Redux Toolkit Query
- TanStack Query
- SWR

Decision

Использовать TanStack Query.

Consequences

Плюсы

- зрелая библиотека;
- удобное кэширование;
- отличная интеграция с React.

Минусы

- потребуется изучение библиотеки.

---

# Именование

Формат файлов:

0001-state-management.md

0002-auth.md

0003-search.md

0004-routing.md

---

# Code Review

Во время ревью необходимо проверить:

□ ADR действительно необходим.

□ Решение описывает одну проблему.

□ Рассмотрены альтернативы.

□ Причины выбора понятны.

□ Последствия описаны.

---

# Запрещается

❌ Создавать ADR для каждой задачи.

❌ Использовать ADR как документацию по реализации.

❌ Переписывать старые ADR.

❌ Принимать архитектурные решения без обсуждения, если они затрагивают весь проект.

❌ Создавать ADR без описания альтернатив.




# Architecture Principles

При выборе архитектурного решения необходимо соблюдать следующие приоритеты (от наиболее важного к менее важному):

1. Простота поддержки.
2. Простота понимания.
3. Предсказуемость поведения.
4. Масштабируемость.
5. Безопасность.
6. Производительность.
7. Скорость разработки.

Если два решения функционально эквивалентны, предпочтение отдаётся более простому.

Запрещается создавать абстракции без реальной необходимости.

Любая новая зависимость должна быть обоснована.

Предпочитать композицию наследованию.

Предпочитать явный код неявному.

Предпочитать стандартные возможности React и TypeScript сторонним библиотекам.



# Technical Debt

Временные решения допускаются только при выполнении всех условий:

- существует отдельная задача на устранение;
- технический долг документирован;
- решение не ухудшает безопасность;
- решение не нарушает архитектуру критических модулей.

Каждый TODO должен содержать ссылку на задачу.

Запрещается оставлять TODO без объяснения причины.



# 12. Code Review

## Цель

Code Review является обязательным этапом разработки.

Цель Code Review:

- обеспечение качества кода;
- предотвращение появления технического долга;
- соблюдение Engineering Standards;
- обмен знаниями внутри команды;
- раннее обнаружение архитектурных проблем.

Code Review не является способом оценки разработчика.

Обсуждается код, а не человек.

---

# Общие принципы

Во время ревью необходимо руководствоваться следующими принципами:

- быть конструктивным;
- объяснять причины замечаний;
- предлагать возможные варианты решения;
- уважать мнение других участников команды.

Замечание без объяснения причины считается плохой практикой.

---

# Что проверяется

Каждый Pull Request должен быть проверен по следующим категориям.

---

## Архитектура

Проверить:

□ соответствует ли код FSD;

□ нет ли нарушения границ слоев;

□ не появилась ли циклическая зависимость;

□ соответствует ли решение существующей архитектуре;

□ не нарушен ли публичный API модулей.

---

## Компоненты

Проверить:

□ компонент имеет одну ответственность;

□ отсутствует лишняя логика в JSX;

□ отсутствует дублирование;

□ нет чрезмерной универсальности;

□ компонент можно переиспользовать при необходимости.

---

## State Management

Проверить:

□ Server State хранится в TanStack Query;

□ UI State не хранится в Query;

□ Derived State не хранится в useState;

□ отсутствует несколько источников истины.

---

## API

Проверить:

□ используется слой API;

□ отсутствуют fetch/axios внутри компонентов;

□ ошибки обрабатываются централизованно;

□ отсутствует логика преобразования DTO внутри UI.

---

## Типизация

Проверить:

□ отсутствует any;

□ отсутствует unknown без последующей проверки;

□ отсутствуют необоснованные type assertion;

□ используются существующие типы.

---

## Производительность

Проверить:

□ нет лишних useMemo;

□ нет лишних useCallback;

□ нет React.memo без необходимости;

□ изображения оптимизированы;

□ отсутствуют очевидные лишние рендеры.

---

## Безопасность

Проверить:

□ нет dangerouslySetInnerHTML;

□ отсутствуют console.log;

□ отсутствует хранение чувствительных данных;

□ новые зависимости обоснованы.

---

## Тестирование

Проверить:

□ добавлены необходимые тесты;

□ отсутствуют нестабильные тесты;

□ тестируется поведение;

□ тесты читаемы.

---

## Документация

Проверить:

□ обновлена документация (если требуется);

□ обновлены типы API (если изменился контракт);

□ создан ADR (если решение архитектурное).

---

# Что не должно становиться замечанием

Во время ревью запрещается требовать:

❌ изменения личного стиля оформления кода;

❌ переименования без объективной причины;

❌ переписывания рабочего кода только потому, что существует другой вариант;

❌ преждевременной оптимизации;

❌ создания дополнительных абстракций без необходимости.

---

# Когда можно отклонить Pull Request

PR должен быть отклонен если:

- нарушена архитектура проекта;
- появляется технический долг без согласования;
- нарушены требования безопасности;
- отсутствует типизация;
- отсутствует обработка ошибок;
- не проходит CI;
- отсутствует необходимое тестирование.

---

# Definition of Approved

Pull Request считается готовым к объединению если:

✓ все замечания устранены;

✓ архитектурные требования соблюдены;

✓ CI успешно завершился;

✓ отсутствуют блокирующие замечания;

✓ решение понятно любому разработчику команды.


# 13. Dependency Management

## Цель

Каждая новая зависимость увеличивает:

- размер bundle;
- вероятность появления уязвимостей;
- сложность обновлений;
- стоимость поддержки проекта.

Поэтому новая библиотека должна добавляться только при наличии объективной необходимости.

---

# Правила

Перед добавлением зависимости необходимо ответить на вопросы:

□ Решает ли библиотека реальную проблему?

□ Можно ли решить задачу средствами React, TypeScript или браузера?

□ Не существует ли уже аналогичной библиотеки в проекте?

□ Поддерживается ли библиотека?

□ Есть ли критические уязвимости?

□ Совместима ли библиотека с лицензией проекта?

---

# Критерии выбора

При выборе библиотеки учитывать:

- активность разработки;
- количество пользователей;
- качество документации;
- совместимость с TypeScript;
- tree-shaking;
- размер bundle;
- скорость релизов.

---

# Обновление зависимостей

Зависимости должны регулярно обновляться.

Каждое обновление должно сопровождаться:

- проверкой changelog;
- запуском тестов;
- проверкой сборки.

---

# Запрещается

❌ Добавлять библиотеку ради одной функции.

❌ Использовать неподдерживаемые библиотеки.

❌ Игнорировать критические security-обновления.

❌ Дублировать функциональность нескольких библиотек.



# 14. Documentation Standards

## Документировать необходимо только то, что невозможно понять из кода.

Не документировать очевидные вещи.

---

# Обязательно документируются

- ADR.

- Нетривиальные архитектурные решения.

- Причины ограничений.

- Особенности интеграции.

- Неочевидные алгоритмы.

- Временные решения.

---

# Не документируются

❌ Очевидный код.

❌ Простые функции.

❌ Getter/Setter.

❌ JSX без сложной логики.

---

# Комментарии

Комментарий должен объяснять

ПОЧЕМУ

а не

ЧТО делает код.

Хорошо

// Используем debounce, чтобы не отправлять запрос после каждого символа.

Плохо

// Увеличиваем i на единицу.

---

# TODO

Каждый TODO должен содержать:

- причину;
- ссылку на задачу.

Запрещено:

TODO: потом исправить





# 15. Refactoring Policy

Рефакторинг допускается если:

- уменьшает сложность;

- уменьшает связность;

- улучшает читаемость;

- не изменяет поведение.

---

Не выполнять массовый рефакторинг одновременно с новой функциональностью.

---

Если изменение поведения необходимо —

оно должно оформляться отдельной задачей.

---

После рефакторинга должны проходить все тесты.

---

Запрещается

❌ Переписывать рабочий код "потому что можно лучше".

❌ Изменять архитектуру без ADR.

❌ Выполнять крупный рефакторинг внутри bugfix.



# 16. Definition of Done

Задача считается завершенной только если:

□ Функциональность реализована.

□ Код соответствует Engineering Standards.

□ Архитектура не нарушена.

□ Нет дублирования.

□ Нет any.

□ Нет TODO без задачи.

□ Нет console.log.

□ Нет ошибок TypeScript.

□ Нет предупреждений линтера.

□ Все тесты проходят.

□ Добавлены необходимые тесты.

□ Обновлена документация.

□ Обновлены типы API (если требуется).

□ Создан ADR (если необходимо).

□ Pull Request успешно прошел Review.

□ CI успешно завершился.

Неправильно

import {...} from "@/entities/product/ui/ProductCard"

Правильно

import {...} from "@/entities/product"

---

Порядок импортов

4. Entities

5. Features

8. App

# 22. TypeScript Rules

Использовать strict mode.

---

Запрещается

any

---

Не использовать

@ts-ignore

Без комментария.

---

Предпочитать

unknown

вместо

any

---

Предпочитать

type

если объединяются типы.

Использовать

interface

для описания объектов.

---

Не использовать enum

если можно использовать union type.

---

Не использовать type assertion

если можно выполнить проверку.

---

Не использовать Non-null assertion (!)

без объективной необходимости.

---

Использовать discriminated unions

вместо множества boolean.

---

Не экспортировать внутренние типы модуля.

button

nav

main

header

section

footer

---

---

---

---

---

Контрастность должна соответствовать WCAG AA.
