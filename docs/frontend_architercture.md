# 0. Purpose

## Назначение документа

Настоящий документ описывает архитектуру Frontend интернет-магазина и является основным источником информации о структуре приложения.

Документ определяет:

- архитектуру приложения;
- организацию модулей;
- взаимодействие между слоями;
- правила масштабирования;
- организацию бизнес-модулей;
- работу с API;
- организацию состояния приложения.

Если Engineering Standards отвечает на вопрос **«Как разрабатывать?»**, то Frontend Architecture отвечает на вопрос **«Как устроено приложение?»**.

Настоящий документ распространяется только на Frontend.

Backend рассматривается как независимая система.

---

## Scope

Документ описывает архитектуру MVP.

Функциональность, отсутствующая в MVP, намеренно не рассматривается.

При дальнейшем развитии проекта архитектура расширяется без изменения существующих принципов.

---

## Цели архитектуры

Архитектура должна обеспечивать:

- масштабируемость;
- простоту сопровождения;
- возможность параллельной разработки;
- низкую связанность модулей;
- высокий уровень переиспользования кода;
- независимость Frontend от Backend.

---

## Связанные документы

При разработке необходимо использовать следующие документы:

- Product Requirements
- Engineering Standards
- OpenAPI Specification
- ADR

При возникновении противоречий применяется следующий порядок приоритетов:

## Общий принцип взаимодействия

Frontend полностью независим от внутренней реализации Backend.

Единственной точкой взаимодействия является HTTP API.

Frontend не должен содержать знаний о внутренней архитектуре Backend.

Любое изменение Backend не должно требовать изменения архитектуры Frontend при сохранении API-контракта.

---

## Основной поток данных

Все пользовательские действия проходят один и тот же путь.

```
User Action

↓

React Component

↓

Feature

↓

API Layer

↓

Go Backend

↓

Response

↓

TanStack Query Cache

↓

UI Update
```

Данные всегда проходят через единый API Layer.

UI не взаимодействует с Axios напрямую.

---

## Высокоуровневые подсистемы

Frontend разделён на несколько независимых подсистем.

### Presentation Layer

Отвечает за отображение интерфейса.

Содержит:

- Pages
- Widgets
- UI Components

---

### Business Layer

Содержит бизнес-логику приложения.

Включает:

- Features
- Entities

---

### Infrastructure Layer

Отвечает за:

- API Client
- роутинг;
- конфигурацию;
- обработку ошибок;
- работу с серверным состоянием.

---

### Shared Layer

Предоставляет общие ресурсы проекта:

- UI Kit;
- Hooks;
- Utilities;
- Types;
- Constants;
- Config;
- Assets.

Shared не должен содержать бизнес-логику.

---

## Основные принципы взаимодействия

Архитектура строится по следующим правилам:

- страницы собираются из Widget;
- Widget используют Feature;
- Feature работают через Entity;
- Entity используют Shared;
- Shared не зависит от других слоев.

Нарушение данного порядка запрещено.

---

## Основные свойства архитектуры

Архитектура должна обеспечивать:

- независимость модулей;
- предсказуемую структуру;
- простое масштабирование;
- возможность повторного использования компонентов;
- возможность разработки несколькими разработчиками одновременно.

Все новые возможности должны интегрироваться в существующую архитектуру без изменения уже реализованных модулей.

# Основные подсистемы

Архитектура Frontend состоит из следующих независимых подсистем.

## Application Layer

Отвечает за запуск приложения.

Включает:

- точку входа;
- глобальные провайдеры;
- конфигурацию приложения;
- роутинг верхнего уровня.

Application Layer не содержит бизнес-логики.

---

## Presentation Layer

Отвечает исключительно за отображение пользовательского интерфейса.

Содержит:

- Pages;
- Widgets;
- UI Components.

Presentation Layer не должен выполнять HTTP-запросы и не должен содержать бизнес-логику.

---

## Business Layer

Реализует бизнес-логику интернет-магазина.

Содержит:

- Features;
- Entities.

Business Layer отвечает за обработку пользовательских сценариев.

---

## Infrastructure Layer

Предоставляет инфраструктурные сервисы.

Включает:

- API Client;
- маршрутизацию;
- управление серверным состоянием;
- конфигурацию приложения;
- обработку ошибок;
- логирование (при необходимости).

Infrastructure Layer не должен содержать бизнес-логику.

---

## Shared Layer

Предоставляет общие ресурсы приложения.

Содержит:

- UI Kit;
- общие компоненты;
- Hooks;
- Utilities;
- Types;
- Config;
- Assets;
- Constants.

Shared Layer является фундаментом приложения.

Shared Layer не должен зависеть от бизнес-модулей.

---

Каждое пользовательское действие проходит одинаковый путь.

```

↓

UI Component

↓

Feature

↓

API Client

↓

Backend

↓

Response

↓

↓

React

↓
```

Все обращения к серверу проходят через единый API Layer.

Компоненты пользовательского интерфейса не должны выполнять HTTP-запросы напрямую.

---

# Поток данных

Архитектура использует однонаправленный поток данных.

```
Backend

↓

API Client

↓

TanStack Query

↓

Feature

↓

Widget

↓

Page

↓

Browser
```

Каждый уровень отвечает только за свою область ответственности.

Изменение данных должно происходить через соответствующий слой архитектуры.

---

# Независимость модулей

Каждый модуль должен обладать следующими свойствами:

- минимальная связанность;
- высокая связность внутри модуля;
- независимость реализации;
- возможность локального изменения;
- возможность повторного использования.

Изменение одного бизнес-модуля не должно требовать изменения остальных модулей приложения.

---

# Масштабируемость

Архитектура должна позволять:

- добавление новых страниц;
- добавление новых Feature;
- добавление новых Entity;
- расширение каталога;
- подключение новых сервисов;
- создание мобильного клиента;
- дальнейшее развитие продукта без полного переписывания Frontend.

Каждое новое архитектурное решение должно быть совместимо с существующей структурой приложения.


# 3. Architectural Decisions

## Назначение

Данный раздел фиксирует ключевые архитектурные решения проекта и причины их принятия.

Цель раздела — обеспечить единое понимание архитектуры всеми участниками команды и предотвратить повторное обсуждение уже принятых решений.

Все решения, описанные ниже, являются базовыми для MVP и могут быть изменены только посредством ADR (Architectural Decision Record).

---

## React

### Решение

В качестве библиотеки пользовательского интерфейса используется React.

### Причины выбора

- зрелая и стабильная экосистема;
- большое профессиональное сообщество;
- высокая производительность;
- широкая поддержка TypeScript;
- большое количество готовых решений;
- удобство масштабирования проекта.

---

## TypeScript

### Решение

Весь Frontend разрабатывается исключительно на TypeScript.

### Причины выбора

- статическая типизация;
- уменьшение количества ошибок;
- безопасный рефакторинг;
- улучшенная поддержка IDE;
- повышение читаемости кода.

Использование JavaScript в исходном коде проекта не допускается.

---

## Vite

### Решение

В качестве инструмента сборки используется Vite.

### Причины выбора

- быстрый запуск проекта;
- высокая скорость HMR;
- современная система сборки;
- простая конфигурация;
- отличная интеграция с React.

---

## Rendering Strategy

### Решение

На этапе Frontend MVP приложение работает как SPA на React + Vite с MSW.

Перед публичным production-запуском storefront переводится на React Router Framework Mode с SSR для динамических страниц и prerendering для статических страниц.

### Границы этапов

MVP:
- SPA;
- клиентская маршрутизация;
- MSW;
- корзина остаётся клиентской.

Production:
- SSR: страницы категорий и товаров;
- prerendering: главная, контакты, политика, соглашение;
- корректные HTTP-статусы 200, 404 и 500;
- корзина не индексируется и остаётся клиентской.

### Требования к MVP-коду

Код MVP должен быть совместим с будущим SSR:
- не обращаться к `window`, `document` и `localStorage` при импорте модулей;
- выполнять browser-only действия только в обработчиках событий или эффектах;
- не смешивать API-клиент с UI;
- получать SEO-данные из моделей категорий и товаров;
- не завязывать роуты на MSW;
- не использовать случайные данные в публичных блоках.

Целевая стратегия и блокировка публичного релиза зафиксированы в
`docs/adr/0001-rendering-strategy.md`. Её реализация выполняется отдельной миграционной
задачей до production-релиза.

---

## Feature-Sliced Design

### Решение

Основной архитектурой проекта является Feature-Sliced Design.

### Причины выбора

- низкая связанность модулей;
- высокая масштабируемость;
- предсказуемая структура проекта;
- удобная параллельная разработка несколькими разработчиками;
- упрощение сопровождения.

---

## React Router

### Решение

Навигация реализуется через React Router.

### Причины выбора

- зрелость решения;
- официальная поддержка React;
- удобная организация маршрутов;
- гибкость настройки.

---

## TanStack Query

### Решение

Server State управляется исключительно через TanStack Query.

### Причины выбора

- кэширование данных;
- автоматическая синхронизация;
- повторные запросы;
- инвалидация кэша;
- снижение количества собственного кода.

Использование других механизмов управления Server State допускается только после оформления ADR.

---

## Axios

### Решение

Все HTTP-запросы выполняются через единый API Client на основе Axios.

### Причины выбора

- interceptors;
- централизованная обработка ошибок;
- единая конфигурация запросов;
- удобная работа с авторизацией в будущем;
- возможность масштабирования.

Прямое использование fetch в коде проекта не допускается.

---

## CSS Modules

### Решение

Основным способом стилизации являются CSS Modules.

### Причины выбора

- локальная область видимости стилей;
- отсутствие конфликтов имен;
- простая интеграция с Vite;
- отсутствие необходимости в runtime.

Использование других подходов к стилизации допускается только после согласования командой.

---

## Zod

### Решение

Валидация пользовательских данных и схем API выполняется через Zod.

### Причины выбора

- совместимость с TypeScript;
- единый подход к валидации;
- безопасное преобразование данных;
- уменьшение количества runtime-ошибок.

# 4. Feature-Sliced Design

## Назначение

В качестве основной архитектуры Frontend используется Feature-Sliced Design (FSD).

FSD определяет правила организации исходного кода, распределения ответственности между слоями приложения и взаимодействия между ними.

Основные цели использования FSD:

- разделение ответственности;
- снижение связанности модулей;
- упрощение сопровождения проекта;
- возможность параллельной разработки несколькими разработчиками;
- предсказуемая структура проекта;
- возможность масштабирования без изменения существующей архитектуры.

Настоящий раздел описывает применение FSD именно в рамках данного проекта.

---

## Основные принципы

Архитектура строится вокруг бизнес-функциональности, а не вокруг типов файлов.

Проект разделяется на независимые модули, каждый из которых отвечает за собственную область ответственности.

Каждый модуль должен быть максимально автономным и иметь минимальное количество зависимостей от остальных частей приложения.

---

## Архитектурные слои

В проекте используются следующие слои:

```
app/
pages/
widgets/
features/
entities/
shared/
```

Каждый слой имеет строго определённую ответственность.

Размещение файлов вне соответствующего слоя запрещается.

---

## Правило зависимостей

Все зависимости направлены исключительно сверху вниз.

```
App
 │
 ▼
Pages
 │
 ▼
Widgets
 │
 ▼
Features
 │
 ▼
Entities
 │
 ▼
Shared
```

Обратные зависимости запрещены.

Например:

✔ Допустимо

```
widgets → features
```

✔ Допустимо

```
features → entities
```

✔ Допустимо

```
entities → shared
```

✖ Недопустимо

```
shared → entities
```

✖ Недопустимо

```
entities → features
```

✖ Недопустимо

```
features → pages
```

✖ Недопустимо

```
widgets → pages
```

---

## Публичный API слоя

Каждый модуль обязан предоставлять публичный API.

Взаимодействие между слоями допускается исключительно через публичный API модуля.

Импорт внутренних файлов другого модуля запрещён.

Допустимо:

```ts
import { ProductCard } from "@/entities/product";
```

Недопустимо:

```ts
import ProductCard from "@/entities/product/ui/ProductCard/ProductCard";
```

Наличие публичного API обеспечивает:

- инкапсуляцию;
- возможность внутреннего рефакторинга;
- снижение связанности;
- стабильность импортов.

---

## Decision Tree

При добавлении нового кода разработчик обязан определить уровень ответственности.

Порядок принятия решения:

```
Это новая страница?

│

├── Да → pages

│

└── Нет

      │

      Это композиция нескольких блоков интерфейса?

      │

      ├── Да → widgets

      │

      └── Нет

            │

            Это пользовательский сценарий?

            │

            ├── Да → features

            │

            └── Нет

                  │

                  Это бизнес-сущность?

                  │

                  ├── Да → entities

                  │

                  └── Нет → shared
```

При возникновении сомнений предпочтение отдаётся более низкому уровню архитектуры.

Если решение остаётся неоднозначным, оно обсуждается командой и фиксируется в ADR.

| Необходимо реализовать | Архитектурный слой |
|-------------------------|--------------------|
| Отдельную страницу | `pages` |

## 4.1 App Layer

### Назначение

Слой `app` является точкой входа Frontend-приложения.

Он отвечает за инициализацию приложения, подключение глобальных провайдеров, конфигурацию окружения и запуск маршрутизации.

Данный слой не содержит бизнес-логики интернет-магазина.

---

### Ответственность

App Layer отвечает исключительно за инфраструктуру приложения.

В частности:

- инициализацию React;
- подключение React Router;
- подключение TanStack Query;
- регистрацию Error Boundary;
- регистрацию глобальных Provider;
- настройку Theme;
- подключение глобальных стилей;
- конфигурацию приложения;
- обработку верхнеуровневых ошибок.

---

### Разрешено

В слое `app` допускается размещение:

- точки входа приложения (`main.tsx`);
- корневого компонента `App`;
- Provider;
- Router Provider;
- Query Client;
- Theme Provider;
- Error Boundary;
- глобальных Layout;
- глобальной конфигурации приложения.

---

### Запрещено

В слое `app` запрещается размещать:

- бизнес-логику;
- HTTP-запросы;
- работу с сущностями предметной области;
- пользовательские сценарии;
- компоненты страниц;
- компоненты каталога;
- компоненты корзины;
- компоненты товаров.

---

### Структура

Пример структуры слоя:

```text
app/
├── providers/
├── router/
├── layouts/
├── styles/
├── config/
├── App.tsx
└── main.tsx
```

Структура может расширяться по мере развития проекта, однако ответственность слоя остаётся неизменной.

---

### Правила взаимодействия

App Layer является самым верхним уровнем архитектуры.

Он может использовать любой нижележащий слой.

Ни один слой проекта не должен импортировать код из `app`.

---

### Примеры

Корректные примеры:

- подключение Router;
- подключение QueryClientProvider;
- подключение ThemeProvider;
- регистрация глобальных Layout;
- регистрация ErrorBoundary.

Некорректные примеры:

- функция поиска товаров;
- карточка товара;
- компонент корзины;
- оформление заказа;
- запрос списка товаров.


## 4.2 Pages Layer

### Назначение

Слой `pages` представляет отдельные страницы приложения.

Каждая страница соответствует одному маршруту (Route) и является точкой входа пользователя в определённый пользовательский сценарий.

Страница не должна содержать сложную бизнес-логику.

Её задача — собрать необходимые Widget, определить композицию страницы и передать параметры нижележащим слоям.

---

### Ответственность

Pages Layer отвечает за:

- отображение маршрутов;
- композицию Widget;
- получение параметров маршрута;
- организацию структуры страницы;
- подключение SEO-метаданных (если применимо);
- обработку состояния страницы (loading / error / empty).

---

### Разрешено

В Pages допускается:

- использовать Widget;
- использовать Feature;
- использовать Entity;
- использовать Shared;
- работать с параметрами URL;
- формировать структуру страницы.

---

### Запрещено

Страницы не должны:

- выполнять HTTP-запросы напрямую;
- содержать бизнес-логику;
- реализовывать пользовательские сценарии;
- выполнять сложные вычисления;
- содержать крупные переиспользуемые компоненты.

---

### Структура

```text
pages/

catalog/

product/

cart/

favorites/

profile/

not-found/
```

Каждая страница представляет отдельный маршрут приложения.

---

### Правила взаимодействия

Pages могут использовать:

- Widgets;
- Features;
- Entities;
- Shared.

Pages не должны импортироваться другими слоями.

---

### Примеры

Корректные примеры:

- Catalog Page;
- Product Page;
- Cart Page;
- Profile Page;
- Favorites Page.

Некорректные примеры:

- Product Card;
- Search Component;
- Add To Cart Button;
- Favorite Button.


## 4.3 Widgets Layer

### Назначение

Слой `widgets` отвечает за композицию пользовательского интерфейса.

Widget представляет собой самостоятельный крупный блок страницы, объединяющий несколько компонентов, Feature и Entity в единый пользовательский блок.

Widget не является бизнес-сущностью и не реализует отдельный пользовательский сценарий полностью.

Главная задача Widget — собрать интерфейс из более мелких модулей.

---

### Ответственность

Widgets Layer отвечает за:

- композицию пользовательского интерфейса;
- объединение нескольких Feature;
- объединение нескольких Entity;
- построение крупных блоков страниц;
- повторное использование крупных UI-блоков.

---

### Разрешено

Widget может использовать:

- Features;
- Entities;
- Shared.

Widget может:

- отображать данные;
- управлять расположением компонентов;
- объединять несколько Feature;
- получать данные через нижележащие слои.

---

### Запрещено

Widget не должен:

- выполнять HTTP-запросы напрямую;
- хранить глобальное состояние;
- содержать бизнес-логику;
- импортировать Pages;
- импортировать другие Widget напрямую, если это приводит к циклическим зависимостям.

---

### Структура

```text
widgets/

header/

footer/

catalog-grid/

product-gallery/

breadcrumbs/

sidebar/

search-panel/
```

Каждый Widget представляет собой независимый переиспользуемый блок интерфейса.

---

### Правила взаимодействия

Widget может использовать:

- Features;
- Entities;
- Shared.

Widget не должен импортировать Pages.

Widget не должен знать о маршрутизации приложения.

---

### Примеры

Widget:

✔ Header

✔ Footer

✔ Product Gallery

✔ Catalog Grid

✔ Breadcrumbs

✔ Search Panel

Не Widget:

✖ Product Card

✖ Add To Cart Button

✖ Favorite Button

✖ Search Request

---

### Когда создавать Widget

Widget создаётся, если одновременно выполняются условия:

- объединяет несколько компонентов;
- используется как самостоятельный блок страницы;
- может повторно использоваться на нескольких страницах;
- не представляет отдельную бизнес-сущность.

Если блок используется только один раз и не предполагает повторного использования, допускается оставить его внутри соответствующей Page до появления второго сценария использования.



## 4.4 Features Layer

### Назначение

Слой `features` реализует пользовательские сценарии (User Actions).

Feature отвечает за действие пользователя, а не за отображение сущности.

Feature представляет собой законченную бизнес-операцию, которую пользователь может выполнить в приложении.

---

### Ответственность

Features Layer отвечает за реализацию пользовательских сценариев.

Например:

- поиск;
- фильтрация;
- сортировка;
- добавление товара в корзину;
- удаление товара из корзины;
- добавление в избранное;
- оформление заказа;
- авторизация;
- регистрация.

Feature объединяет интерфейс, бизнес-логику и взаимодействие с API, необходимые для выполнения одного действия.

---

### Разрешено

Feature может использовать:

- Entities;
- Shared.

Feature может:

- обращаться к API;
- изменять серверное состояние;
- использовать TanStack Query;
- выполнять валидацию данных;
- содержать локальное состояние, необходимое для выполнения сценария.

---

### Запрещено

Feature не должен:

- импортировать Pages;
- импортировать Widgets;
- зависеть от других Feature без явной необходимости;
- содержать код, относящийся к нескольким независимым пользовательским сценариям.

---

### Структура

```text
features/

search/

catalog-filter/

sort-products/

add-to-cart/

remove-from-cart/

favorite/

checkout/

authentication/
```

Каждый Feature реализует один пользовательский сценарий.

---

### Правила взаимодействия

Feature может использовать:

- Entities;
- Shared.

Feature не должен знать о структуре страниц.

Feature не должен управлять расположением элементов интерфейса.

---

### Примеры

Feature:

✔ Add To Cart

✔ Remove From Cart

✔ Search Products

✔ Catalog Filters

✔ Product Sorting

✔ Login

✔ Registration

Не Feature:

✖ Product

✖ Category

✖ Header

✖ Catalog Page

---

### Правило одной ответственности

Один Feature реализует один пользовательский сценарий.

Недопустимо объединять несколько независимых действий в один Feature.

Например:

✔ add-to-cart

✔ favorite

✖ product-actions

Такой подход обеспечивает независимость модулей и упрощает сопровождение проекта.



## 4.5 Entities Layer

### Назначение

Слой `entities` представляет бизнес-сущности предметной области.

Entity описывает объект, существующий независимо от пользовательского интерфейса и конкретных пользовательских сценариев.

Entity инкапсулирует данные, типы, модели и базовое представление бизнес-сущности.

---

### Ответственность

Entities Layer отвечает за:

- описание бизнес-моделей;
- хранение типов;
- отображение бизнес-сущностей;
- преобразование данных;
- работу с моделями предметной области.

Entity не реализует пользовательские сценарии.

---

### Разрешено

Entity может содержать:

- типы;
- модели;
- базовые UI-компоненты;
- API конкретной сущности;
- функции преобразования данных;
- схемы валидации.

---

### Запрещено

Entity не должен:

- импортировать Features;
- импортировать Widgets;
- импортировать Pages;
- содержать пользовательские сценарии;
- управлять маршрутизацией приложения.

---

### Структура

```text
entities/

product/

category/

cart/

order/

user/
```

Состав сущностей может расширяться по мере развития продукта без изменения архитектурных принципов.

---

### Правила взаимодействия

Entity может использовать только Shared.

Entity является независимой единицей предметной области.

Каждая Entity должна иметь собственный публичный API.

---

### Примеры

Entity:

✔ Product

✔ Category

✔ User

✔ Cart

✔ Order

Не Entity:

✖ Search

✖ Checkout

✖ Header

✖ Product Page

---

### Правило независимости

Каждая Entity должна быть максимально независимой.

Изменение одной Entity не должно требовать изменения других Entity, если отсутствует прямая бизнес-зависимость.

При необходимости взаимодействия между сущностями координация должна происходить через слой Features.

## 4.7 Common Mistakes

### Назначение

Данный раздел описывает наиболее распространённые ошибки при использовании Feature-Sliced Design.

Цель раздела — обеспечить единообразную архитектуру проекта и уменьшить количество архитектурных ошибок во время разработки.

---

### Ошибка №1

#### Размещение бизнес-логики в Pages

❌ Неправильно

Page самостоятельно выполняет HTTP-запросы, обрабатывает данные и реализует бизнес-логику.

Почему это плохо:

- страница становится трудно сопровождаемой;
- снижается переиспользуемость;
- нарушается разделение ответственности.

✔ Правильно

Page собирает интерфейс из Widget и Feature.

---

### Ошибка №2

#### Превращение Widget в Feature

Widget отвечает за композицию интерфейса.

Feature отвечает за пользовательский сценарий.

Например:

✔ Header → Widget

✔ Product Gallery → Widget

✔ Search Products → Feature

✔ Add To Cart → Feature

---

### Ошибка №3

#### Создание слишком крупных Feature

Feature должен реализовывать один пользовательский сценарий.

❌ Плохо

```
product-actions/
```

Внутри:

- добавить в корзину;
- удалить;
- избранное;
- сравнение;
- рейтинг.

✔ Хорошо

```
add-to-cart/

favorite/

rate-product/
```

Каждый сценарий развивается независимо.

---

### Ошибка №4

#### Использование Shared как "папки для всего"

Shared предназначен исключительно для общего кода.

Запрещается помещать в Shared:

- бизнес-логику;
- сущности;
- пользовательские сценарии;
- компоненты страниц.

Если код относится к предметной области, он должен располагаться в соответствующем Entity или Feature.

---

### Ошибка №5

#### Импорт внутренних файлов другого модуля

❌ Недопустимо

```ts
import ProductCard from "@/entities/product/ui/ProductCard";
```

✔ Правильно

```ts
import { ProductCard } from "@/entities/product";
```

Все взаимодействие между слоями осуществляется исключительно через Public API.

---

### Ошибка №6

#### Создание циклических зависимостей

Недопустимо:

```
Feature A

↓

Entity

↓

Feature A
```

или

```
Widget A

↓

Widget B

↓

Widget A
```

Архитектура должна оставаться ацикличной.

---

### Ошибка №7

#### Преждевременная декомпозиция

Не следует создавать отдельный Feature или Widget только потому, что "в будущем он может пригодиться".

Новые модули создаются тогда, когда появляется реальная необходимость в их повторном использовании или самостоятельной ответственности.

---

### Ошибка №8

#### Нарушение принципа единственной ответственности

Каждый модуль отвечает только за одну область ответственности.

Если модуль начинает выполнять несколько независимых задач, его следует разделить.

---

### Ошибка №9

#### Дублирование компонентов

Перед созданием нового компонента необходимо проверить:

- существует ли аналогичный компонент;
- можно ли расширить существующий;
- соответствует ли новый компонент правилам архитектуры.

Без необходимости дублирование запрещается.

---

### Ошибка №10

#### Проектирование "на будущее"

Архитектура MVP должна решать текущие задачи проекта.

Не допускается создание сложных абстракций, дополнительных слоёв или универсальных механизмов без подтверждённой бизнес-потребности.

Каждое архитектурное решение должно быть обосновано реальным сценарием использования.
